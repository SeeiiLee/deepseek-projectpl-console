## 1. 已核验的注入机制（事实基础，全部对上游源码验证过）

我（DeepSeek Harness 会话中的 Agent）的上下文由四层组成：

| 层 | 机制 | 关键事实 |
|---|---|---|
| L1 System | system-prompt 注册表（section/context/tool/variable），每次请求重新组装 | identity(-100) → persona(0) → 工具指南(100–199)；插件可注册自有 section（order −50 留给我们）；同名 section 冲突即失败；complete:true 会排掉其他普通 section |
| L2 Runtime Snapshot | 动态 context provider，**变化时才追加** user-role 快照，新快照取代旧快照 | 只放机器/部署/会话状态；不放人类规则；快照只能缩小权限、不能反向授权 |
| L3 AGENTS.md | agent-instructions：$DSH_HOME/AGENTS.md + project root 到 cwd 祖先链 + 第一方 read/write/edit 触达发现的嵌套规则 | AGENTS 是 user-role 持久消息（system-reminder 只是外观），**留在历史里直到压缩，不是只计费一次**；不覆盖 System 与直接用户指令 |
| L4 会话历史 | 完整消息 + 压缩检查点（有损摘要） | 压缩会丢细节；规则相关消息与压缩的交互必须专门设计（第 3.9 节） |

### 1.1 三个承重陷阱（已实测确认）

1. **project root 陷阱**：没有 root marker（默认 .git）时，project root 回退为会话 cwd；Personal 没有 .git；且真实桌面会话 cwd 是上游 D:\Deepseek Harness（main.js 不设 DSH_WORKSPACE_ROOT，harness 回退 sourceRoot）。→ Personal 根 AGENTS.md 在真实会话里走项目根链大概率加载不到，只能指望文件工具触达发现（跨树行为未验证）。
2. **complete prompt 绕过**：minimal preset 的 persona 是 complete:true + includeRuntimeContext:false，会排掉 Personal System Policy 与快照。→ System Policy 必须配 profile 覆盖验证。
3. **order ≠ 权限**：order 只决定拼接顺序；权威来自角色（System > 用户指令 > 具体 AGENTS > 宽泛 AGENTS）与机器门禁。

## 2. 本轮讨论的全部结论

### 2.1 对我上一轮结论的三处纠正（已承认并采纳）

1. 「AGENTS 几乎免费」是错的：AGENTS 基线通常只追加一次，但作为持久历史进入后续每轮请求直到压缩；真实优势是「不重复追加副本 + 可能有 KV 前缀缓存 + 可按项目选择性加载」。
2. 「先放 AGENTS 观察遗忘率再升 System」对不可逆红线风险过高：忘记一次就可能不可逆的规则，应从第一天进 System 并配机器门禁。
3. 只创建 Personal 根 AGENTS 而不解决发现链 = 假安全感。

### 2.2 最终采纳的治理架构

```text
Personal System Policy（插件注册，order -50，6–10 条跨项目不可协商红线）
        ↓
Runtime Snapshot（当前机器、部署、路径、权限、版本、Gate 状态；纯机器事实）
        ↓
Global AGENTS（$DSH_HOME/AGENTS.md：跨项目稳定流程与规则路由）
        ↓
Project / Nested AGENTS（项目与子树增量规则 + 精确任务路由表）
        ↓
按任务读取详细规则、架构、协议与事故记录
        ↓
Machine Gates（危险动作的最终硬拦截；只能缩小权限，不能授权）
```

内容分类三个维度：**权威要求**（违反一次是否不可逆）、**适用范围**（跨项目/仅 Personal/仅子树）、**变化频率**（稳定/偶变/每次运行都变）。按维度决定去向，而不是只看 token。

### 2.3 两条权威链（必须分开）

行为指令权威链（高→低）：平台/System/Developer 约束 → Personal System Policy → 当前用户对本任务的明确指令 → 更具体 Nested AGENTS → Project AGENTS → Global AGENTS → 详细文档解释。

事实可信度链（高→低）：当前源码/Schema/数据库结构/运行探针/制品/机器 Gate → 未过期的 Runtime Snapshot → 当前状态文档（NEXT/BLOCKED/compat/PROGRESS）→ DEVLOG 与事故记录 → 模型记忆或口头回忆。

## 3. Agent 架构调整清单（要开发的插件与要建的规则面）

### 3.1 Personal System Policy 插件（第一优先级）

- 通过 Personal 插件正规扩展点注册：ctx.systemPrompt.section({ name, order, text })。
- 名称唯一：personal:cross-project-policy；order -50；普通 section（不用 complete）；不得叫 deployment:persona；不做同名 shadow。
- 红线文本（已按 Codex 二次评审 §5 修订，Cyrus 2026-08-15 拍板；插件注册仍须按第 3.11 节批准）：

```text
你必须遵守以下跨项目工作红线：

1. 审计、评审、解释和诊断请求默认为只读；除非当前任务明确要求实施，否则不执行修改。
2. 删除、覆盖、不可逆变更、系统配置、安装、commit、push、发布、发送/外发、外部状态写入、付费调用和真实数据写入，必须获得针对明确对象与范围的当前授权。
3. 不得输出、记录或外泄凭据、密钥、令牌、原始敏感个人数据及未经授权的敏感项目数据；涉及敏感内容的联网查询同样必须先确认。
4. 必须区分已验证事实、合理推断、待决定方案和未知；没有可复现证据，不得声称完成。
5. 开工前识别当前适用规则、项目身份与受保护范围；信息不足时可以继续安全的只读核验，但规则冲突、身份不明或安全状态不明时必须停止危险动作并显式报告。
6. 不得绕过、削弱或静默跳过权限、安全、隐私、发布和数据完整性门禁；门禁通过只表示技术条件满足，不代表用户已经授权。
7. 失败必须显式呈现；不得静默降级、伪造成功或用过时文档掩盖当前状态。发生数据或运行时事故时，立即停止进一步写入、保留证据、确认恢复点并显式报告。
8. 在满足目标的前提下，优先采用范围最小、可验证、可回滚且不污染无关区域的方案。
```

- 覆盖范围（拍板）：standard、code、cordis 及所有具备写工具的 workflow/goal 子代理、自动续轮；minimal/complete 在不能注入等价红线前不得用于可写项目任务，仅可作无文件写入、无敏感数据的隔离测试并显式标识「不受 Personal Policy 覆盖」。
- 文本带版本/内容哈希供诊断，但版本号不渲染进模型正文；修改需 diff + 审阅 + 测试 + 回滚点。

### 3.2 Global AGENTS（$DSH_HOME/AGENTS.md）

- 承载：跨项目协作原则、证据与授权要求、规则文件定位方法。
- 注意：stable 的 DSH_HOME 是 F:\documents\Cyrus Deepseek Harness Data\harness-home（受保护），dev 是 %USERPROFILE%\.dsh（受保护）→ **投影动作必须逐次过红线审批**。规范源放 Personal 仓库，经受控脚本投影 + 哈希校验；禁止各 home 手工维护漂移。

### 3.3 Personal 根 AGENTS（路由器，不是百科全书）

- 结构：Scope → 权威与事实源 → 不可协商项目规则 → 开工检查清单 → 任务路由表（触发条件 + 精确文件路径 + 章节 anchor + 读取时机 + stop gate）→ 稳定命令 → 完成证据。
- 加载前提：先解决 project root 发现（固定会话 cwd / 显式传 project root / 靠 $DSH_HOME 或 System Policy 兜底；跨树文件工具触达发现仅作补充，不作保证）。

### 3.4 Nested AGENTS

- 只在子树有独特稳定规则时建（Project Control 单写者协议、发布/安装目录、Electron 生命周期、插件 seam 与 schema、敏感数据目录）；只写相对父级的增量，不复制全文。

### 3.5 Runtime Snapshot 扩展

- 机器生成结构化数据再渲染短文本：schemaVersion、generatedAt、expiresAt、profile、workspaceRoot、projectRoot、dshHome、userData、protectedRoots、approvalMode、sandboxMode、networkAccess、sourceRevision、gateSummary、以及 desktop 特有字段（PROJECT_CONTROL_HOME、BUILD_FLAVOR、harness 实例 id、当前实例 PID/端口所有权）。
- 失效处理：过期标 stale；缺失字段 unknown；受保护路径或审批状态未知时危险动作默认拒绝；快照只能陈述事实，不能授权。

### 3.6 机器门禁（Machine Gates）

- 门类：文件与路径（受保护根、递归删除、symlink 穿越）、进程与生命周期（仅已验证 PID）、外部动作与成本（二次确认/报价）、隐私与凭据（secret scan、PII 脱敏）、构建与发布（revision/哈希一致、快照新鲜度、制品真实性）、规则治理（check:governance：AGENTS 存在与加载链、omission/truncation、路由 anchor 有效、易变数字未写死、快照未过期、System Policy 在允许 profile 真实出现、无 complete 绕过）。
- 原则：门禁只能缩小权限；通过只表示技术条件满足，不代表用户已批准。

### 3.7 有效 prompt 检查机制（本手册补充的缺失项）

- 需要一个诊断插件挂在 system-prompt/assemble waterfall 上，供 check:governance 与验收使用。没有它，验收矩阵一半不可测。
- 默认只输出 manifest：section 名称 / order / 来源 / 长度 / 内容哈希 / 是否 complete / 是否被 shadow / 是否截断；不落盘完整 prompt 正文。
- 全文诊断必须：用户显式开启 → 只写本机加密诊断目录 → 先脱敏 → 带自动过期时间 → 不进普通日志、Git 与发布包。（Codex 评审 §5.12）
### 3.8 Skill 内容治理（本手册补充的缺失项）

- available_skills 目录与调用时注入的 SKILL.md 是第五通道：Personal skill-library 的 Skill 内容同样受红线约束；与 AGENTS/System 冲突时，安全边界优先，冲突上报 BLOCKED。

### 3.9 压缩交互机制（本手册补充的缺失项）

- 目标不是让某条历史消息「永久免压缩」，而是：关键规则能由权威源重新生成，压缩后由机制自动重注入，并验证重注入内容与作用域一致。System Prompt 本身不是历史消息，不适用「免压缩」概念（Codex 评审 §5.13 措辞修正）。
- 记忆召回注入同样适用：压缩或新会话后须能从记忆库重新检索，不依赖旧消息残留。验收必须含「压缩后规则恢复 + 压缩后记忆可重查」测试。
### 3.10 继承矩阵草案（本手册补充的缺失项）

| 组合类型 | System Policy | Global/Project AGENTS | Runtime Snapshot | 需要验证 |
|---|---|---|---|---|
| 主对话 Agent（standard profile） | 有 | 有（按 cwd 链） | 有 | 有效 prompt 检查 |
| workflow 子代理（agent()） | 待定 | 待定 | 待定 | 子代如何组装 |
| ralph 每轮新 Agent | 待定 | 待定 | 待定 | 同上 |
| Doubt fresh-context 子代理 | 待定 | 待定 | 待定 | 同上 |
| goal 自动续轮 | 有（同会话） | 有 | 有 | 快照跨轮更新语义 |
| minimal/complete preset | 被排除 | 待定 | 被排除 | 明确禁止或记录例外 |

### 3.11 授权映射（本手册补充的缺失项）

| 动作 | 授权要求 |

### 3.12 事故应急子句（常驻）

- 发生数据或运行时事故：立即停止进一步写入 → 保留证据 → 确认恢复点 → 最小恢复 → 显式报告。此句应进 System Policy 或 Project AGENTS 顶部，不能只埋在手册里。

## 4. 记忆系统蓝图（本手册的核心增量）

目标：长期记忆 + 跨会话记忆稳定保存，覆盖规则、经验、事故与项目事实。载体允许本地 SQL/DB 文件、文档文件、乃至向量数据库。

### 4.1 分级模型（L0–L4）

| 级别 | 内容 | 权威载体 | 注入方式 |
|---|---|---|---|
| L0 红线 | 不可协商安全/隐私/授权边界（8 条） | System Policy 插件 | 每轮必在 |
| L1 稳定方法 | 工作方法、验证阶梯、路由规则、稳定命令 | Global/Project AGENTS | 会话开始时注入，压缩后需重注入 |
| L2 项目事实 | 当前指针、协议、Schema、状态、架构 | 源码/Schema/状态文档/机器快照 | 显式读取 + 快照；一个事实一个来源 |
| L3 经验与事故 | 坑、根因、可复用规则、事故史 | 经验索引 + postmortem/DEVLOG | 任务路由触发读取；升级到 L1/L0 有评审流程 |
| L4 会话历史 | 已做决定与过程的原始证据 | 上游 Session 存储（原生） | 跨会话召回机制 |

> 命名分层（Codex 评审 §5.1 采纳）：L0–L4 是**内容归属分类**（什么东西放哪），不是记忆库自己的生命周期。实现层另用两套正交命名，避免把治理面误当成记忆库可写对象：
> - 治理面：G0 System Policy / G1 AGENTS / G2 Machine Gates / G3 Runtime Snapshot —— 记忆系统只能提交升级建议，不能直接修改。
> - 记忆面：M0 Candidate（status=candidate 的候选）/ M1 Active（活跃 claim：status=active，authority=user_confirmed 等）/ M2 Procedural（程序化 Skill）/ M3 Evidence（来源与证据）/ M4 Archive（已失效）。
> 映射：L0→G0；L1→G1（程序化后→M2）；L2→G3 + 当前状态源；L3→M0/M1；L4→M3 + 上游 Session 存储。

### 4.2 存储选型（按职责，不搞单一万能库）

| 事实 | 存储 | 理由 |
|---|---|---|
| 经验条目、事故记录、升级状态 | 本地 SQLite（Personal 自有库，如 memory.sqlite3） | 结构化、单写者、可加 revision/状态/时间戳；与 Project Control 库分开 |
| 规则正文与路由 | docs/ 下 Markdown + AGENTS 路由引用 | 可 diff、可审阅、可被 AGENTS 机制直接读 |
| 跨会话语义检索 | P4 本地 bge-m3 ONNX + SQLite 派生向量索引 + FTS5/RRF | v0.3.0 已发布；无模型或索引异常时降级 FTS5；进入大规模门前修复最近 512 条向量覆盖限制 |
| 会话原始历史 | 上游 Session 存储 + Codex 只读源/加密归档 | 不把所有消息复制成长期记忆；通过 evidence index、locator 和 candidate 提炼进入治理闭环 |
| 凭据 | 系统凭据库 | 只存引用，永不进记忆库 |

> v4 落地形态：经验库采用 catalog + Global/Private/Project 分片（9.2/9.12）；P4 向量已上线；P5 的 observation、Procedure、feedback 和运行 trace 继续使用同一 canonical store/审计体系，不另建第二套事实库。

### 4.3 写入闭环（经验怎么变成记忆）

```text
DEVLOG / postmortem：保留原始事实与过程
        ↓
经验索引（SQLite）：提炼根因、触发条件、可复用结论、状态
        ↓
高频且每次必知 → 升级 Project/Global AGENTS
        ↓
跨项目且忘记一次不可接受 → 压缩升级 System Policy
        ↓
可机械判断 → 实现为测试或机器 Gate
        ↓
已失效 → 标记 superseded/archived，退出默认阅读路径
```

- 写入从“三通道”升级为“通道 + 审批控制”（详见 9.5）：显式记忆、自动候选、机器事实继续保留；Memory Admission Controller 额外区分 evidence-only、candidate、policy-auto active、user-confirmed 和 deny/quarantine。自由生成的 LLM 总结、Reflection 和 Procedure 仍不得直接 active；只有低风险、同项目、可确定性复核、无冲突且可撤销的内容，才允许按策略由 Agent 自动批准。
- 升级前必答五问：根因是否确认？当前版本是否仍复现？适用单模块/单项目/跨项目？是行为原则、当前事实还是机器可检查条件？是否已有权威来源？
- 条目字段：标题/日期/现象/根因/影响/触发条件/当时修复/可复用规则/对应测试或 Gate/验证证据/最后核验日期/状态(active|superseded|archived)/被何取代。

### 4.4 召回机制（记忆怎么回到上下文）

先由 Context Compiler 判断「本任务是否需要历史、哪些上下文值得进入、投入多少 token 是否能降低总任务成本」。简单翻译/改写、当前消息自带全部上下文、用户明确要求不参考历史 → 跳过检索、零注入。需要历史时采用“常驻内核 + 常驻知识目录 + 任务相关包 + 按需深证据”，而不是把 system 目录全部塞入或全部省略。

| 场景 | 召回方式 |
|---|---|
| 每次会话开局 | AGENTS 链（L1）+ 快照（L2 事实） |
| 显式查询 | memory.query 工具（一期唯一记忆召回入口；结果带来源与不可信标记） |
| 自动 quick-pass（P2 起） | 紧凑摘要/目录 → 精确关键词/路径/实体/时间 → FTS5/向量，全程有界 |
| P5 多线索召回 | Retrieval State → ID/Path、FTS、Dense、Temporal、Entity/Causal 多路 → RRF → evidence rerank → 0–2 条或 abstain |
| P5 深度召回 | 首轮无可靠证据且任务值得深挖时，才启用 Latent Cue/最多两轮再检索；图只是可选候选通道 |
| 跨会话旧决定 | 上游跨会话召回机制（先摸清其 API 与治理边界） |

- 召回内容必须带来源、日期与状态，不得与当前源码/快照冲突时静默覆盖；冲突走事实可信度链。召回结果不得进 System section，不得当作机器当前状态注入 Runtime Snapshot。
### 4.5 一致性与安全

- 一个事实一个权威来源；记忆库条目与文档、AGENTS、System 的投影必须有内容哈希校验与漂移检查（check:governance）。
- 记忆库存本机；索引可含摘要不含原文敏感数据；发布前脱敏；受保护路径不进入记忆库正文。
- 记忆库备份按在线一致性快照纪律（better-sqlite3 backup() + integrity_check + manifest，见 9.9.4），不采用运行中 copy 文件；记忆库纳入受保护路径守卫之外的明确归属。

## 9. 记忆系统详细架构 v4（基座实现 + P5 统一架构）

> 修订说明：v3 的可信、隔离、可恢复基座继续有效；v4 吸收 Hindsight、Letta Code、MemoraX、Daydream 与人脑记忆检索研究的可验证启发，新增 Memory Intelligence Engine、Memory Admission Controller、Context Compiler、Observation/Procedure/Outcome 合同。P5 不再定义为“图谱化”，图降为可选候选通道。
> 总方针：「先把记忆做成可信、隔离、可恢复的索引系统，再用可度量、可回退的方式增加自动治理、上下文编译和经验学习」。
> 本文不授权实现：进入任何阶段前按第 3.11 节授权映射逐项获得 Cyrus 批准；所有验证先走临时 fixture，不碰稳定数据。

### 9.1 目标与非目标

**目标**：
1. 跨会话、跨重启的稳定记忆：L0–L4 内容各归其位（G/M 实现命名见 4.1 注）。
2. 本地优先：存储、嵌入、召回全部本机；无 embedding 时 FTS5 词法召回，功能不缺席。
3. 可信召回：每次召回带来源、日期、状态；召回内容标记「不可信参考」，不得覆盖 System/用户指令/当前源码事实。
4. 经验升级闭环：M0→M1→M2(Skill)→G1(AGENTS)→G0(System)→G2(Gate)→M4(归档)；治理面变更只能由记忆系统提议、由人与流程执行。
5. 隔离与可恢复：不串项目（越界召回=0）、可导出、可迁移、可删除、可恢复、可解释、可评测。
6. 与现有治理完全咬合：System Policy、AGENTS、Runtime Snapshot、机器门禁、发布红线、受保护路径守卫、check:governance。

**非目标（明确不做，除非 Cyrus 另行决定）**：
1. 不做团队/云端协作中枢（Tencent 式 hub）——单人本地桌面为唯一场景。
2. 不复制上游 Session 存储：会话原文留在官方存储，记忆库只存「提炼后 claim + 引用 + 哈希 +（可选）加密最小摘录」。
3. 不把凭据、密钥、令牌存入记忆库；Restricted 级内容不入正文。
4. 不引入第二套状态源：不重复存 Project Control 的 WorkItem/Review/Decision；项目身份优先复用其注册表（9.3.1）。
5. 记忆同步 git 远端推送暂不做，外发动作单独审批。

### 9.3 控制面：项目身份与 scope

#### 9.3.1 项目身份：复用 Project Control project_id（Codex 二次评审 §3.1/决策 6）

- **身份唯一来源**：Project Control 的 project_id。已核验：docs/PROJECT_CONTROL_DATA_MODEL.md——两个项目入口收敛同一种稳定 project_id（L15）、路径/文件夹名/Git remote 只能用于发现不能当 ID（L46）、projectId 创建后不可修改或复用（L112）；plugins/project-control/migrations/0001_core_control_plane.sql 已有 STRICT projects 表与 workspace_locations 路径绑定。**记忆系统不得自建第二套 projects/project_uuid 注册表。**
- 读取方式：经 Project Control Host API 读取身份与路径绑定（其控制面 SQLite 约定只有唯一 Host 可读写，记忆插件不得直接打开该库）。
- 身份规则：路径是 locator；分支是项目视图，不默认独立项目；worktree 同 project_id；stable/dev/test 是 deployment flavor，不是项目身份。
- Session 绑定（决策 6 方案 D）：Session 创建/切换项目时显式绑定 project_id + locationRef/workspaceRoot；launcher/Project Control 传 workspaceRoot；managed 项目用 project.yaml 的 projectId marker 验证；Personal 默认根只作未选择项目时的安全 fallback。
- 身份不明/冲突：只读检查、禁止长期写入、禁止跨项目召回、提示选择/注册项目；marker 与 DB 冲突 → quarantine（停止长期写入）。

```sql
-- 记忆侧目录（catalog.sqlite3）：只存记忆自身事实；不复制 Project Control canonical 元数据
CREATE TABLE memory_projects(
  project_id TEXT PRIMARY KEY,       -- 引用 Project Control projects.project_id（唯一身份源）
  memory_policy_id TEXT,
  sensitivity_class TEXT NOT NULL DEFAULT 'internal'
    CHECK (sensitivity_class IN ('public','internal','sensitive','restricted')),
  retention_policy TEXT,
  shard_locator TEXT NOT NULL,       -- 相对 locator：projects/<project_id>/memory.sqlite3（不写绝对路径主键）
  source_revision INTEGER,           -- 最近同步的 Project Control revision（cache 用途）
  is_cache INTEGER NOT NULL DEFAULT 0 CHECK (is_cache IN (0,1)),
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL
) STRICT;
-- 显示名称/别名/路径/生命周期以 Project Control 为 canonical；如需在此缓存，必须带 source_revision 且 is_cache=1，并保证可随时重建
```
#### 9.3.2 scope 与默认访问规则（Codex §7.5 采纳 + 二次评审 §3.3 修正）

```text
global_user   经确认、跨所有项目的用户偏好（属个人隐私，存 private/user 分片，不进 global/patterns）
portfolio     仅一个项目群内共享的方法/结论（模型支持；共享 allowlist 初始为空）
project       单一项目稳定记忆（默认主 scope；scope_id = Project Control project_id）
workspace     特定 worktree/实验分支的临时记忆（可选，可折入 project 覆盖）
```

- candidate 是生命周期状态（status），不是 scope；session 暂存不进长期 claims——放独立 inbox/staging 或上游 Session，确认后才转入长期 scope。
- 默认召回访问：当前 workspace/project → 所属 portfolio 中明确 allowlist 的 pattern → active global_user（authority=user_confirmed）。**跨项目检索默认关闭**；用户明确要求「比较多个项目/复用其他项目经验」才扩大 scope，并在结果中显示来源项目。
- 不得默认对全库做向量/图搜索；scope 是硬过滤，不是排序加分。
- tag/entity/file/module/error/time 等是**门内软索引**：用于分类、生成检索线索和排序，不能创建访问权或绕过 `project_id`。执行顺序固定为 `project_id/allowlist 硬过滤 → status/authority/version/sensitivity 硬过滤 → tag/实体/关键词/向量/关系检索`。
- 某项目经验需要跨项目复用时，不修改原 claim 的 project scope；由 Curator 生成一个新的 global/portfolio pattern candidate，去掉项目私有细节并经用户确认后才共享。
#### 9.3.3 跨项目 pattern/playbook（Codex §7.6 采纳）

晋升为 kind=pattern 的条件（全满足）：
1. 在两个以上独立项目验证过；
2. 有明确适用边界与反例；
3. 不含项目特有路径、业务数据、用户隐私；
4. Cyrus 确认允许跨项目；
5. 有来源链与最近验证日期；
6. 可执行时优先提升为 Skill（M2），不留在语义节点。

#### 9.4.3 修正后的 SQLite Schema（分片库；Codex §5.7 + 二次评审 §3.3–§3.7 全部问题）

```sql
-- 全部表 STRICT；枚举用 CHECK；删除语义见本块末尾对照表。
CREATE TABLE claims(
  id TEXT PRIMARY KEY,                        -- uuidv7
  scope_kind TEXT NOT NULL CHECK (scope_kind IN ('global_user','portfolio','project','workspace')),
  scope_id TEXT NOT NULL,                     -- 非空（修 NULL 唯一键失效）：user:<id> / portfolio_id / project_id / workspace_id
  kind TEXT NOT NULL,
  canonical_text TEXT NOT NULL,
  searchable_text TEXT NOT NULL DEFAULT '',   -- 派生检索文本（ASCII 词 + 中文二元组，写入时计算；可整体重建）

  extractor_id TEXT, extractor_version TEXT,

  created_at TEXT NOT NULL, updated_at TEXT NOT NULL,
  UNIQUE(scope_kind, scope_id, kind, normalized_content_hash)
) STRICT;
CREATE INDEX idx_claims_scope ON claims(scope_kind, scope_id, kind, status);
CREATE INDEX idx_claims_status ON claims(status, updated_at);

CREATE TABLE evidence_sources(
  id TEXT PRIMARY KEY,
  kind TEXT NOT NULL CHECK (kind IN ('repo_file','rollout','session','command','artifact','user_confirmation')),
  portable_locator TEXT NOT NULL,   -- project://<project_id>/docs/NEXT.md#x 或 session://<id>#<turn>
  local_locator TEXT,               -- 本机绝对路径（可变，仅作解析 alias；导出时默认省略/重绑定）

) STRICT;

CREATE TABLE claim_relations(
  source_id TEXT NOT NULL REFERENCES claims(id) ON DELETE CASCADE,
  target_id TEXT NOT NULL REFERENCES claims(id) ON DELETE CASCADE,

  weight REAL NOT NULL DEFAULT 1.0,
  created_at TEXT NOT NULL,
  PRIMARY KEY(source_id, target_id, kind)
) STRICT;

-- FTS5：external-content + 触发器同步
CREATE VIRTUAL TABLE claims_fts USING fts5(searchable_text, content='claims', content_rowid='rowid');
CREATE TRIGGER claims_ai AFTER INSERT ON claims BEGIN
  INSERT INTO claims_fts(rowid, searchable_text) VALUES (new.rowid, new.searchable_text);
END;
CREATE TRIGGER claims_ad AFTER DELETE ON claims BEGIN
  INSERT INTO claims_fts(claims_fts, rowid, searchable_text) VALUES('delete', old.rowid, old.searchable_text);
END;
CREATE TRIGGER claims_au AFTER UPDATE ON claims BEGIN
  INSERT INTO claims_fts(claims_fts, rowid, searchable_text) VALUES('delete', old.rowid, old.searchable_text);

-- 向量（P4 才启用）：派生索引，可整体重建；备份可不含向量
CREATE TABLE embeddings(
  claim_id TEXT PRIMARY KEY REFERENCES claims(id) ON DELETE CASCADE,
  provider_id TEXT NOT NULL, model_id TEXT NOT NULL, model_revision TEXT NOT NULL,

  idempotency_key TEXT PRIMARY KEY,  -- project_id|session_id|turn_seq|extractor_version|candidate_index

  original_claim_hash TEXT,
  outcome TEXT NOT NULL DEFAULT 'pending' CHECK (outcome IN ('pending','expired','rejected','promoted')),
  expires_at TEXT,
  created_at TEXT NOT NULL

-- 召回审计：默认脱敏，不存完整 query

-- 删除证明：只留不可逆 id/hash/时间/原因，不留原文
CREATE TABLE tombstones(
  id TEXT PRIMARY KEY, scope_kind TEXT NOT NULL, scope_id TEXT NOT NULL,
  content_hash TEXT, deleted_at TEXT NOT NULL, reason TEXT NOT NULL

CREATE TABLE meta(key TEXT PRIMARY KEY, value TEXT NOT NULL) STRICT;
-- schemaVersion / migrations / lastMaintenance / lastBackup / embeddingGeneration
```

- 删除语义对照表（二次评审 §3.7）：claims 物理删除时，在**同一事务**内——写 tombstone → claims_fts 触发器同步删除 → embeddings CASCADE → claim_evidence CASCADE（evidence_sources 保留，孤儿由维护任务清理）→ claim_relations 两侧 CASCADE → recall_items.claim_id SET NULL → candidate_idempotency.claim_id SET NULL（幂等键与 outcome 保留）→ superseded_by SET NULL。任何一步失败整体回滚。
- candidate 到期：先标 outcome=expired/rejected，再按独立清理策略物理删除，不被外键阻断。
- 向量检索实现决策（不变）：P4 先在 scope 过滤后的小候选集（≤64 条）上 brute-force 余弦；只有规模压测证明 O(N) 不可接受时，才评估 Windows 上可稳定部署/备份/迁移的 ANN 扩展，且向量表带 generation 可整体重建。
- 候选 staging 实现决策（不变，简化自 Codex §7.1）：候选 = claims 表 status=candidate + TTL，存于目标分片内；减少目录与迁移面。
- P5 authority/approval 扩展：`policy_auto` 不得伪装成 `user_confirmed`。实现时可扩 `authority_class`，也可增加正交 `approval_class`；无论采用哪种，必须能查询、排序、降级和批量撤销。
- P5 observation 最小合同：source_memory_ids、proof_count、contradiction_count、factual/valid time、snapshot/watermark、full/delta、current/candidate diff、history、retrieved-vs-used 和 generator/policy version。proof_count 只是支持度，不是正确性。
#### 9.4.4 状态机（二次评审 §3.4：两轴正交，无 confirmed 中间态）

```text
lifecycle_status = candidate | active | disputed | superseded | archived
authority_class = user_confirmed | repo_verified | machine_observed | llm_extracted

candidate ──用户确认──▶ active + user_confirmed
active ──冲突/质疑──▶ disputed（停止自动晋升，进人工评审队列）
active ──被取代/失效──▶ superseded / archived（退出默认召回）
任意状态 ──用户删除──▶ tombstone（单事务级联，见 9.4.3）
```

- 候选获确认直接变 active + user_confirmed，无中间 confirmed 态；disputed 停止自动晋升进人工评审；archived 只留审计；删除写 tombstone 并与级联同事务；备份中的副本按保留期自然过期。
### 9.5 写入架构：三条来源通道 + 一个审批控制器

#### A. 显式记忆通道（canonical 写入唯一即时路径）

```text
用户明确请求（「记住这条」「以后所有项目都这样做」）
  → 分类 scope / sensitivity / retention
  → 回显准备保存的精简 claim（1–3 句）
  → 必要时确认（user_profile、跨项目等敏感类必须确认）
  → status=active + authority_class=user_confirmed 写入 + provenance + revision
```

#### B. 自动候选通道（LLM 不得直接写 canonical）

```text
turn / task end（默认关闭，按项目 opt-in）
  → 本地规则先过滤敏感内容（secret / PII 扫描）
  → 有界 LLM 提取候选（Host 侧适配器，复用识图插件模式）
  → schema 校验 + 幂等键（project_id|session_id|turn_seq|extractor_version|candidate_index）
  → status=candidate + TTL（默认 14 天）
  → 批量评审 / 用户确认 → active + user_confirmed 或自动过期
```

#### C. 机器事实通道（不写长期自然语言记忆）

版本、路径、测试、构建、schema 等机器事实进 Runtime Snapshot / 当前状态文档 / artifact manifest / provenance 指针。记忆库只存「在哪里重新确认」与「该事实曾用于什么决定」。

#### D. Memory Admission Controller（P5）

来源通道决定“内容从哪里来”，Admission Controller 决定“它能进入什么状态”：

| 动作 | 结果 | 边界 |
|---|---|---|
| A0 evidence-only | 只登记事件/hash/locator | 不生成自然语言当前事实 |
| A1 candidate | 自动提取、History/Reflection/Procedure 输出 | 默认不进入普通召回 |
| A2 policy-auto active | 由 Agent 按确定性策略批准 | 必须低风险、同项目、可复核、无冲突、可撤销；权威低于用户确认 |
| A3 user-confirmed | 用户确认后 active | 决策、偏好、覆盖、跨项目、Procedure/Skill、安全/权限规则 |
| A4 deny/quarantine | 拒绝或隔离 | 密钥、禁止类型、scope 冲突、来源不明、高风险推断 |

自由生成的 LLM 结论不能凭自评置信度进入 A2。A2 仅用于增加可验证证据、合并完全重复来源、规范化低风险机器结果等；自动审批按 kind/project 有额度和 kill switch，被用户纠正后该策略自动降级。

#### 写入前安全管线（12 步，Codex §9.2 采纳）

project_id/scope 解析 → secret 扫描 → PII/敏感分级 → 数据最小化 → canonicalization → 精确去重（复合唯一键）→ 冲突/时效/supersede 检测 → authority/approval 标注 → retention 赋值 → schema 校验 → 短事务写入 → 事务后异步 embedding（P4 起）。

#### 自动写入默认策略（Codex §9.4 采纳）

| 类型 | 默认政策 | 存储位置 |
|---|---|---|
| 工作沟通偏好 | 用户确认后允许 | private/user 分片，可跨项目召回 |
| 非敏感项目方法/架构决定 | 有来源、项目内允许 | Project 分片 |
| 客户名称、合同要点、经营策略、配方/工艺 | 默认关闭；每项目显式 opt-in | 加密 Project 分片，禁止跨项目 |
| 个人健康、情绪、家庭/私人关系 | 永不自动保存；仅明确「请记住」才可候选 | private 加密分片 |
| 原始医疗/遗传报告 | 不存正文，只存安全 locator 或不存 | Restricted 引用 |
| 身份证、银行卡、电话、详细地址、账号 | 永不保存 | 无 |
| 密码、密钥、token、cookie | 永不保存（写入门禁硬拒绝） | 系统凭据库只存秘密本体 |
| 当前测试数/插件数/进度 | 不存自然语言事实，只存事实源指针 | Runtime/状态文档/provenance |

- 涉及第三方个人信息（如「邮件抄送某人」）保存前也需确认；用户修改政策只影响未来写入，历史条目列出由用户决定删除/重分类/保留。
- kind × scope 配对硬规则（2026-08-15 增补）：global_user 只收 global_fact/user_profile/pattern/skill；project 只收 project_fact/event/task/skill/pattern；项目级内容落全局会被拒绝。前置归类用 memory_classify 建议 + record 硬校验。
### 9.6 召回架构：Context Compiler + 多路有界召回

#### 需求门（不做每轮自动召回）

- 跳过：简单翻译/改写、当前消息已含全部上下文、与项目无关的简单事实、用户明确要求不参考历史。
- quick pass：提到具体项目/模块/历史决定、要求延续之前约定、任务含糊可能受项目约束、涉及长期偏好/事故/迁移/兼容性、当前事实与历史可能冲突。

#### Context Compiler（P5-R1）

上下文分四层：Kernel（每轮必在的项目身份/安全/授权/召回协议）、Catalog（system/AGENTS/Procedure/关键记忆目录摘要）、Task Pack（当前阶段/文件/错误/工具/实体/时间相关正文）、Deep Evidence（按需展开的完整来源和旧版链）。优化目标是“初始上下文 + 后续检索 + 重复推理 + 工具调用 + 返工”的总成本，而不是机械压低首轮 token。

每项装载记录 `reason/scope/freshness/estimated_value/token_cost`。Recall 子代理默认接收 Light/Standard 检索任务包，不复制整段原始对话；只有前两级无结果、高风险或复杂因果任务才升级 Deep。

#### 渐进检索顺序

```text
0. 判断是否需要历史；不需要则零检索
1. 解析当前 Project Control project_id / workspace / 任务类型
2. project/scope/status/authority/version/sensitivity 硬过滤
3. Retrieval State：任务、阶段、文件、实体、错误、工具、失败尝试、时间
4. 并行候选：ID/Path、FTS5、Dense、Temporal、Entity/Causal
5. RRF 合并、精确/语义去重、Evidence Reranker
6. 校验来源、时效、supersede、冲突与当前事实源
7. 注入 0–2 条最小证据包；必要时再展开 bundle/来源
8. 首轮无 supported hit 且值得深挖时，才用 Latent Cue/最多两轮再检索
9. 仍无可靠证据或超预算则明确 abstain
```

#### 排序信号（Codex §10.3 采纳）

硬门优先于排序：`project_id` 决定允许搜索的范围，tag/entity/vector 只能在门内找内容。加分：当前 project/workspace 精确匹配 · active + user_confirmed/repo_verified · 精确关键词/ID/路径 · 当前版本适用 · 来源可访问 · last_verified_at 新 · 时间/实体/因果匹配 · 任务类型匹配 · 语义相似 · 多项目验证的 portfolio pattern。

惩罚：candidate/disputed/superseded/archived · 来源 unavailable · llm_extracted/policy_auto 低权威 · 长期未验证 · 与当前源码/快照冲突 · 同类重复 · retrieved 但经常 ignored/harmed。图中心性、proof_count、召回频率和点击不能压过 scope/status/authority/factual_at/supersede。

#### 召回包格式（注入单元）

```text
[Historical memory; untrusted and possibly stale]
scope: project/<project_id>  status: active  authority: user_confirmed  last_verified_at: ...
source: rollout/file/session locator
claim: 一到三句精简内容
conflict: none|present
```

默认不注入完整图路径或 bundle；只有关系链/表格/代码/图片引用确实帮助当前推理时，才按预算展开最小必要片段。

#### 预算（同时限制）

最大条目数 · 最大字节/token · 单项目条目上限 · 单一 kind 上限 · 详细证据读取数 · 自动召回耗时 · embedding 调用次数。超预算先保证 scope 正确 → status 正确 → 来源可用 → 多样性 → 冲突项成对出现 → 最具体内容优先（不是简单按 importance 截断）。

#### 注入 seam 决策（Codex §5.4/§10.6 采纳，修正我方原缺陷）

- **当前基座（P1–P4）**：显式 memory.query + 已验证的有界 quick-pass；结果不进 System Policy 或 Runtime Snapshot。
- **P5**：Kernel/Catalog 可作为稳定的小型上下文契约；Task Pack/Deep Evidence 仍使用任务级注入/工具消息。验证不同 query 不错误互覆、token 不单调膨胀、压缩后可重建、子代理不继承错误项目记忆。
- 明确禁止：systemPrompt.context 承载任务级召回（该 seam 语义是「机器当前状态快照，新替旧」，与检索结果生命周期冲突）。
- 召回文本始终低权威：标记不可信、不得调用工具、不得改变权限、不得覆盖用户指令。

#### 引用义务

模型使用某条记忆**影响关键决定**时才输出可见引用（claim id、来源 locator、last_verified_at、是否现场重新验证）；普通回答不要求每条都带内部 id。来源失效时必须说明「这是未重新验证的历史记忆」。

### 9.7 升级闭环 v2（G/M 分离；Codex §5.1/§9.5 采纳）

```text
M0 candidate ──用户确认──▶ M1 active + user_confirmed
M1 ──多次复用且步骤稳定──▶ M2 Skill（对接 skill-library：SKILL.md + 触发条件/输入合同/步骤/脚本/验证清单）
M1 ──跨项目且每次必知──▶ G1 AGENTS 路由条目（diff 审阅后由人执行）
M1 ──跨项目且忘记一次不可接受──▶ G0 System Policy 建议（Cyrus 逐条确认）
M1 ──可机械判断──▶ G2 测试 / 机器 Gate
M1 ──已失效──▶ M4 superseded / archived（退出默认召回）
M1 ──两个以上项目验证且通用──▶ pattern / playbook（仍属记忆面；执行化优先 M2）
M1 ──多条高权威来源支持──▶ observation_candidate ──审批──▶ active observation
M1 + 成功轨迹/结果证据 ──▶ procedure_candidate ──复现与确认──▶ M2 Skill
```

- 触发（三选一）：同一经验跨会话召回 N 次 / 显式标记「以后每次都要遵守」/ CONFLICTS_WITH 命中。
- 评审：Memory Intelligence Engine 的四 Profile 输出结构化建议、diff 和来源（默认不直接执行）；memory.upgrade_propose 只产 promotion_events 记录。
- 硬前置（第 4.3 节五问）：根因确认？当前版本仍复现？适用范围？行为原则/当前事实/机器可检查？是否已有权威来源？
- 治理面变更一律走既有 diff/审阅/测试/回滚流程；记忆系统永不直接改 System/AGENTS/Gate。

### 9.8 生命周期与维护

- Hot/Warm/Cold（Codex §11.2 采纳）：

| 层 | 内容 | 默认召回 |
|---|---|---|
| Hot | active（authority=user_confirmed/repo_verified）、当前版本适用、近期验证、重要项目约束 | 是 |
| Warm | 低频经验、已完成阶段、可按关键词找到 | 按需 |
| Cold | superseded/archived、旧会话、旧版本证据 | 否，只用于审计 |

- 候选 TTL：默认 14 天；到期先标 outcome=expired/rejected，再按独立清理策略物理删除（幂等键与 outcome 保留，见 9.4.3）。
- 重要性与时效分开：importance 表示“忘记代价”，freshness/validity 表示“现在是否仍适用”。复用频率或用户点击不得自动把旧事实变成当前事实；归档和删除继续分开。
- 去重与合并：精确重复可按 A2 自动合并来源；语义近似、冲突、覆盖、scope 提升由 Memory Doctor 先出 diff，保留 SUPERSEDES/历史后再审批。
- observation refresh：支持 preview/dry-run、full/delta、snapshot/watermark、current/candidate diff、来源漂移、retrieved-vs-used 和回滚；二阶 observation 默认 candidate。
- 定期维护任务（effect + disposer，每次有界）：candidate 过期、冲突/版本链扫描、来源可用性复查、FTS/embedding 对账、备份新鲜度、Doctor 报告；低优先级队列不得抢占主对话。
- 用户数据权利（Codex §14.8 采纳）：explain / list_sensitive / correct（保留 supersede 链）/ export / delete（live+索引即时，备份按保留期，tombstone 证明）/ pause / reset_project（双重确认）。

### 9.9 安全与运维

#### 9.9.1 威胁模型与数据分级（Codex §14.1/§14.2 采纳）

威胁（至少覆盖）：其他本地进程读未加密库 · 备份盘丢失 · A 项目会话召回 B 项目敏感内容 · 仓库文档/历史记忆含 prompt injection · 自动提取保存密钥/健康/身份 · embedding endpoint 配错到远程 · 恶意 symlink/reparse point · 日志/诊断泄露内部规则与记忆 · vendor 依赖漏洞或未预期联网 · 库被篡改且哈希被重算 · 过时记忆冒充当前事实 · 删除请求只删 live 库而备份永久保留。

| 等级 | 示例 | 策略 |
|---|---|---|
| Public | 公开项目文档指针 | 普通项目索引 |
| Internal | 内部架构、非敏感经验 | 本地加密、按项目隔离 |
| Sensitive | 个人偏好、商业策略、私人记录 | 独立 private/project shard，严格召回 |
| Restricted | 凭据、令牌、原始医疗/遗传等高敏 | 不进记忆正文，只存安全引用或完全禁止 |

embeddings 继承原文敏感等级（不能因「不可读」视为无敏感性）。

#### 9.9.2 加密与密钥（Codex §13.5/§14.3 采纳，实现排期后置）

- 硬门槛（二次评审决策 15）：加密不是「Stable 发布前」的最后包装，而是**第一次写入真实个人/商业记忆前**的硬门槛。加密完成前 P1–P2 只允许合成 fixture；SQLCipher（经 better-sqlite3-multiple-ciphers）或替代方案在 P1 用合成 fixture 验证；验证失败不得静默以明文库进入 Stable。
- P0 合同：threat model、key hierarchy、recovery、rotation、export 加密；P1 完成加密实现 spike + 备份加密 + 恢复演练。
- envelope 方案：每个分片一个随机 data key；日常副本由 DPAPI/Windows 凭据库保护；恢复副本由 Cyrus 保管的 recovery passphrase 加密（可靠密码学库生成 24 词或等价高熵恢复码）；备份只携带被加密的 data key；恢复密钥不与备份同放；每年或重大迁移前做「只用恢复密钥解开测试备份」演练。
- 密钥轮换分级：纸张丢失未确认泄露 → 重新包裹 recovery wrapping key；recovery secret 可能泄露 → 重包裹所有分片 data key、必要时轮换 data key；data key 泄露 → 重加密对应分片。不笼统「换钥匙」。
- 允许的临时回退：仅开发 fixture 可用明文临时库 + 严格 ACL + 合成数据 + 自动销毁；真实 Sensitive/Private 数据不得进入回退路径；BitLocker/ACL 若要作为正式方案，必须 Cyrus 明确认可其威胁边界，不静默降级。
- 补充：catalog.sqlite3 含敏感项目名与路径，同样需要加密，不能因「无正文」而明文。
- 原则：加密密钥不可用 → fail closed，不创建明文替代库。

#### 9.9.3 Host/Renderer 边界与注入防护（Codex §14.4–§14.6 采纳）

- Renderer 无数据库文件路径与任意 SQL 能力；全部走 Host 侧有界 API；参数类型/长度/scope/limit 白名单；SQL 参数化；每次写入重新验证当前项目与授权；archive/delete/export 需确认；工具返回限长脱敏。
- 召回永不进 System Policy；结构化字段 + 明确 delimiter 包裹；转义可能闭合包装的标记；标注来源/scope/日期/status；召回内容不能调用工具或改变权限；untrusted repo 提取内容默认只对该项目可见；检测「忽略之前规则」类注入文本并降权/隔离。
- 内嵌 ONNX embedding：运行时禁用远程模型与自动下载；本地模型目录须通过 manifest、revision、模型/tokenizer 哈希、dtype/pooling/normalization 合同校验；记忆正文只在本机进程内计算；无本地 embedding 时显式降级 FTS，绝不静默切远程。

#### 9.9.4 备份（Codex §5.8/§13 采纳：废弃「运行中 copy + 哈希」）

- 在线一致性快照：better-sqlite3 backup() API（首选）或满足条件时的 VACUUM INTO；禁止 writer 运行时直接复制 WAL 主库文件。
- 频率（决策 1 拍板）：每日一次完整且经 integrity_check 的快照；大升级、schema migration、批量导入/删除前立即一次（危险变更前 RPO=0，快照后暂停相关 writer 再做变更）；确认高价值记忆批次/重要 promotion 后可触发有节流的增量快照。RPO≤24h；单项目 RTO≤2h；季度真实恢复演练。
- 快照后必做：隔离连接打开 → PRAGMA integrity_check → schema 版本校验 → claims/evidence/relations/FTS 数量对账 → manifest + SHA-256 → 记录 snapshot id/时间/来源 revision。
- 保留期（拍板起点；磁盘成本在 P0 用合成规模测算后确认）：每日 14 份 · 每周 8 份 · 每月 12 份 · 迁移前快照保留至验收后至少 30 天 · 项目归档包按项目生命周期。
- 异物理副本（决策 2 拍板）：只写加密、版本化、带 manifest 的不可变 snapshot 到另一物理设备；不做镜像、不做删除同步、不覆盖唯一旧备份；standing authorization 必须限定设备标识/目标根/数据等级/保留期/停止开关；云端暂不启用（未来单独审批，只传客户端已加密包）。
- 3-2-1 本地个人版：3 份逻辑副本、2 种介质/故障域、1 份离线或异机加密副本；同一 F 盘不同目录不构成独立故障域。
- 备份目录必须在 live root 之外（memory-snapshots，见 9.12）；恢复演练（季度）纳入验收矩阵。

#### 9.9.5 恢复流程（Codex §13.6 采纳）

停止目标 writer → 保留损坏现场与日志 → 选择已验证 snapshot → 恢复到临时目录 → 解密并校验 manifest/hash → integrity_check + schema/FTS/关系对账 → 召回回归 + 人工抽样 → 原子切换 active pointer → 只读验证 → 恢复写入 → 记录 incident 与恢复证据。禁止先覆盖唯一损坏库再调查。

#### 9.9.6 迁移与导出（Codex §12 采纳）

- 支持类型：schema 升级 / 插件版本升级 / 项目移目录或磁盘 / 改名 / flavor 间受控迁移 / 整机迁移 / embedding 模型或维度更换 / 单库→分片 / 归档与激活 / Markdown 经验索引导入。
- 路径迁移：验证新根身份 → 更新 Project Control workspace_locations 路径绑定（记忆侧不复制路径 canonical 值）→ 不改 claim scope 与历史 provenance。provenance 同时保留 portable locator（project://<project_id>/docs/NEXT.md#x），本机绝对路径只是 resolver alias。
- 标准导出包（与 SQLite 实现解耦）：manifest.json（格式/schema/插件版本、project uuid、敏感等级、匿名 machine id、counts、embedding 模型/维度、加密信息、文件哈希、是否含 secure excerpts/archived 内容）+ claims/evidence/relations/promotions/tombstones 各 JSONL + schema/version.json + hashes.sha256 + 可选 embeddings（默认可不导出、目标机重建）。凭据、DPAPI 明文密钥、endpoint token 永不进导出包。
- 导入：验证签名/哈希/版本 → 临时目录建新库 → 逐版本 migration → 导入 → 校验数量/唯一键/FTS/关系 → 重绑 project root → 必要时全量重嵌 → 召回回归集 → 人工抽样 → 原子切换 active pointer → 旧库留作只读 rollback。禁止在唯一 live DB 上做不可回滚原地迁移。
- 导出/删除/重置：必须有明确目标、变更预览、双重确认与审计回执（receipt）；evidence.local_locator 导出时默认省略或重绑定，不泄露本机绝对路径。
- schema migration：append-only + from/to + checksum；单个尽量单事务；大重写用 shadow table/新库；migration journal 记开始/完成/回滚；迁移前一致性快照；迁移后 integrity_check + FTS 对账 + 外键对账 + 召回回归；不支持的旧版本显式拒绝。
- embedding generation：模型/维度变更建新 generation、后台分批重建、完整覆盖并通过回归后切换、旧向量保留回滚窗口、无 embedding 时 FTS 照常。

#### 9.9.7 stable/dev/test 边界（Codex §12.7 采纳 + 我方受保护路径红线）

- Dev 不得直接打开 Stable live DB；测试用合成 fixture 或脱敏只读导出；Stable→Dev 导出须显式批准并检查敏感等级；Dev→Stable 只能导入评审过的 schema/migration；迁移先临时目录验证；不与运行中 Stable writer 并发改同一文件。
- 受保护路径红线不变：稳定版/测试版数据目录是「应用运行时按设计写入」区域；我的自动化（冒烟/清理/迁移脚本）仍受 protected-paths 守卫约束不得触碰。

#### 9.10.4 智能层的逐层准入门槛

### 9.14 风险与开放问题

4. SQLCipher 原生依赖在 Windows Electron 的构建风险 → 已前置为 P1 spike（决策 15）；验证失败不允许静默明文进 Stable，明文+ACL 仅限合成 fixture（BitLocker/ACL 若要作正式方案须 Cyrus 明确认可威胁边界）。
5. 候选积压/backpressure → TTL + 队列有界 + 自动候选永远低优先级，不阻塞用户主任务。
6. 提取 LLM 调用成本（P3 起）→ 低配模型/可关/报价纪律先行。
7. 压缩交互 → 第 3.9 节规则（权威源重注入 + 压缩后记忆可重查测试）。
8. 记忆污染（错误记忆固化）→ 确认门 + CONFLICTS_WITH + 评审 + 归档 + 用户删除权，不自动删除。
9. 向量维度/模型变更 → generation 不混比 + 全量重嵌 + 回滚窗口。
10. 待定开放问题 → 第 7 章（决策状态与 P0 后确认项）。
11. Project Control 身份接口依赖 → 只经其 Host API 读取，不直连其 SQLite；接口不可用 → fail closed（只读、不写记忆）。
12. Agent 自动审批越权 → 只开放 A2 低风险策略，policy_auto 与 user_confirmed 分开，配额/纠正降级/批量撤销/kill switch。

### 决策 1：备份频率（结论：A+）

**结论**：每天做一次完整、经过校验的快照；大升级、数据库结构变更、批量导入/删除**之前**立即再快照一次（这类危险变更前要求「一点不丢」）；确认一批高价值记忆后可加一次快照。平时最多丢 24 小时；单个项目损坏 2 小时内恢复；每季度真做一次「假装硬盘坏了再恢复」的演练。保留份数先按「每日 14 份、每周 8 份、每月 12 份」算，磁盘占用在 P0 用模拟数据测算后再定。

**与初版差别**：初版只按固定时间每天一次；现在加了「危险操作前必快照」和「高价值批次后快照」两个事件触发，比单纯缩短间隔更划算。

**仍需申请**：无额外动作（这只是策略）；实际开发备份功能在 P1 时一并申请。

### 决策 2：备份放到另一块硬盘（结论：B 修订版）

**结论**：可以放另一块物理硬盘/移动硬盘，但**只写加密、带版本号的「不可变快照」**——即每次备份都是完整新文件，绝不做「镜像覆盖」、绝不做「删除同步」（源端误删/中毒不会传染给备份）。你可以给某个固定设备一次性长期授权（限定设备、目录、数据等级、保留期、停止开关）。云端暂不启用。敏感项目备份进移动硬盘需逐项目允许；Restricted 级内容本来就不进记忆库。

**与初版差别**：初版说「插上自动同步」；改为「版本化快照 + 长期授权」，避免镜像把损坏同步过去。

**仍需申请**：第一次实际写外置硬盘前申请（并确认用哪块盘）。

### 决策 3：恢复密钥（结论：A 强化版）

**结论**：用经过审计的密码学库生成 24 词（或同等强度的恢复码），抄两份纸质放两个不同地方；如果你在用密码管理器，可再存一份，但**纸必须是主要副本**。每年做一次「只用这张纸解开测试备份」的演练。钥匙丢了分三级处理：纸丢但没泄露 → 换新纸；纸可能泄露 → 给所有数据换包装；数据钥匙泄露 → 重加密。

**与初版差别**：初版写「换钥匙数据不受影响」太笼统；现在按「丢的是哪把钥匙」分级处理。

**仍需申请**：生成恢复码的时机（加密实施时）单独申请；纸由你保管，我不经手存储位置。

### 决策 4：哪些个人信息允许长期记住（结论：更保守修订表）

**结论**（取代初版表）：

| 内容类别 | 最终政策 | 放哪 |
|---|---|---|
| 工作沟通偏好 | 你确认后允许 | private/user，可跨项目用 |
| 非敏感项目方法/架构决定 | 有来源、项目内允许 | 项目分片 |
| 客户、合同、经营策略、配方/工艺 | **默认关闭，每个项目单独开** | 加密项目分片，禁止跨项目 |
| 健康、情绪、家庭/私人关系 | 永不自动存；只有你明确「请记住」才可进候选 | private 加密分片 |
| 原始医疗/遗传报告 | 不存正文，只存引用或不存 | Restricted |
| 身份证、银行卡、电话、详细地址、账号 | 永不保存 | 无 |
| 密码、密钥、token、cookie | 永不保存（程序硬拒绝） | 凭据库只存本体 |
| 当前测试数/插件数/进度 | 不存，只存事实源指针 | Runtime/文档 |

另：「邮件要抄送某人」这类第三方个人信息，保存前也要你确认。以后改政策只影响未来写入，已存的历史条目列出来由你决定删除/重分类/保留。

**与初版差别**：商业机密从「允许、标敏感」收紧为「默认关闭、按项目开」。

**仍需申请**：无（这是政策）；实际写库在 P1 申请。

### 决策 5：最高规则红线文本（结论：采用二次评审修订 8 条）

**结论**：采用修订版 8 条（全文见第 3.1 节）。要点变化：授权要求「针对明确对象与范围」；新增「敏感项目数据」保护；信息不足时可以继续安全的只读核验、但危险动作必须停；明确「门禁通过 ≠ 已授权」；事故应急子句并入第 7 条常驻。覆盖所有能写文件的 agent/子代理；minimal/complete 两个精简模式在装不下红线前，不得用于可写项目任务。

**与初版差别**：措辞更精确，避免「外发」误伤普通只读联网查询；合并了应急条款。

**仍需申请**：把文本注册进插件 + 验证每个 profile 真实生效（代码动作，单独申请）。

### 决策 6：怎么判断「现在在哪个项目」（结论：新方案 D）

**结论**：不选初版三选一，改用方案 D——**Project Control 已有的 project_id 就是唯一项目身份**（已核实它确实存在且不可修改），会话打开/切换项目时明确绑定「project_id + 工作目录」；Personal 默认根只作没选项目时的兜底。身份不明时：只读、不写记忆、不跨项目召回、提示你选择/注册项目。记忆系统不新建第二套项目表。

**与初版差别**：初版 A（固定目录）只是兜底，不是身份。

**仍需申请**：接 Project Control 接口属代码工作，P1 时申请。

### 决策 7：建本地 Git（结论：同意建，但执行要单独批准）

**结论**：同意为 Personal 工作区建本地 Git、不配任何远程地址。但「同意建」≠「现在建」：初始化前我要先提交「忽略清单 + 敏感内容扫描规则 + 首次提交范围」给你过目，批准后才动手。Git 不承担项目身份（那是决策 6 的事）；commit 每次仍需你批准；push 永远另审。

**与初版差别**：补充了初始化前置审查，并把「建仓」与「提交」都留在批准线后。

**仍需申请**：git init 及首个 commit（提交清单后申请）。

### 决策 8：全局规则投影（结论：B——只投影开发版）

**结论**：规范源放我们自己的仓库；先只投影到开发版目录做验证（投影前给你看 diff、目标路径、哈希；投影后校验生效）；稳定版 F 盘完全不动，等正式安装/升级流程自带。

**与初版差别**：无实质差别，维持初版 B 建议。

**仍需申请**：每次具体投影动作，按受保护路径规则逐次申请。

### 决策 9：《经验.md》去留（结论：A'——严格单向，禁止双向同步）

**结论**：过渡期——经验.md 是正本，数据库只是从它导入的可重建索引（导入记来源哈希，不反写）；系统成熟后——数据库里已确认的条目是正本，经验.md 变成自动生成的只读视图（文件头写明「自动生成，勿手改」，你想改走 memory.correct）。私人/敏感内容不生成进仓库里的 md。

**与初版差别**：初版是「双向同步」；双向会打架（同时编辑、删除复活、敏感内容误导出），改成单向。

**仍需申请**：无（这是策略）；迁移脚本实现时随 P2/P3 申请。

### 决策 10：跨会话记忆用官方还是自建（结论：A）

**结论**：官方会话管「上次聊到哪」和原文；自建库只存提炼后的短条目+来源定位，不复制全文。P0 先摸清官方会话保留多久、删除/导出能力、id 是否稳定；摸不清就把来源标「可能已失效」，也不因此复制原文。

**与初版差别**：无实质差别。

**仍需申请**：无（这是策略）。

### 决策 11：安全护栏顺序（结论：四波）

**结论**：第 1 波先做「路径/文件护栏 + 进程护栏」（防误删误杀，风险最大）；第 2 波做「敏感内容写入护栏 + 外发/联网/安装/付费授权护栏」成对做（检查内容和授权缺一不可）；第 3 波做记忆专属护栏（项目范围、候选/确认、加密就绪、备份新鲜度）；第 4 波做构建发布护栏。

**与初版差别**：把「隐私护栏」和「外部授权」绑成一对；新增记忆专属护栏波次。

**仍需申请**：每一波具体实施单独申请。

### 决策 12：项目分组（结论：支持分组、共享关闭）

**结论**：数据模型支持分组（portfolio 字段），可以分组做统计；但**跨项目共享开关初始为空**——分组不等于共享。等真实出现「这条经验两个项目都要用」时，再逐条创建共享 pattern 并逐条经你确认。

**与初版差别**：初版 B 是「暂不分组」；现在「支持分组、不共享」，为将来留了口子又不增加串味风险。

**仍需申请**：无（这是策略）。

### 决策 13：自动发现值得记住的东西（结论：初期关闭）

**结论**：初期完全关闭，只有你明确说「记住」才记。P3 之后可以试点：只对「项目技术经验/已验证修复/可复用方法」自动发现，每项目单独开、随时可暂停、每周给你一份候选摘要、14 天不确认自动作废、敏感内容自动拦截。

**与初版差别**：无实质差别，维持初版 A 起步。

**仍需申请**：无（这是策略）。

### 决策 14：验收测试规模（结论：两级）

**结论**：分两级。发布基线（必须达标）：10 个活跃项目、40 个归档项目、5 万条活跃记忆、25 万条来源/关系、5 个并发会话，关键词检索 ≤300 毫秒，跨项目泄漏恒为 0。扩展压力（允许性能下降但必须不串项目、不损坏、不丢审计）：30 活跃、100 归档、20 万条、100 万条关系、10 并发。另外还要测库体积、备份窗口、恢复时间等，不只看项目数。

**与初版差别**：初版只按「项目数×3-5」；现在把「必须达标」和「验证余量」分开，并补了非项目指标。

**仍需申请**：无（这是测试目标）。

### 决策 15：加密什么时候启用（结论：第一次写真实数据之前）

**结论**：加密不是「发布前最后一步」，而是**第一次写入真实的个人/商业记忆之前**的硬门槛。加密没完成前，开发只能用合成假数据。加密方案验证失败时，不允许用「明文库」蒙混进稳定版；明文+权限收紧只能存在于开发期的合成数据环境。

**与初版差别**：门槛从「稳定版发布前」提前到「真实数据写入前」。

**仍需申请**：安装加密依赖 + 生成恢复密钥（P1 时申请）。
