## 1. 结论先行

DeepSeek 这次修订是有效的：上一轮指出的主要结构性问题，绝大部分已经被正确吸收。现在的 v2 已经从“概念原型”进步到“可以进入 P0 合同设计和临时 fixture 验证”的程度。

我建议 Cyrus **原则上批准 v2 方向，但不要直接回复“15 项全部按建议执行”**。原因不是总体方向有问题，而是其中几项建议仍需修改：

1. 项目身份不应在“固定 Personal 根 / 当前文件夹 / Git”三者中选一个；现有 Project Control 已经实现稳定 `project_id`，记忆系统应直接复用它。
2. `经验.md` 与数据库不应双向同步；必须只有一个 canonical source，另一份是单向生成视图。
3. 加密不能拖到 P6 才真正落地；可以用合成数据开发，但任何真实个人/商业记忆进入数据库前必须完成 live DB 加密或明确限制为非敏感数据。
4. 备份可以选另一块物理盘，但不建议做“插盘即镜像覆盖”；应写入版本化、加密、不可变快照，并经过范围明确的长期授权。
5. 15 项不是全部都必须在 P0 开始前一次性清零；P0 本来就用于核验技术未知。用户应先拍板价值边界和风险偏好，技术实现细节在 P0 用证据收敛。
6. 修订后的 SQLite Schema 仍有几处真实缺陷：candidate 的 scope/status 混用、`NULL` 唯一键失效、候选删除被外键阻止、状态机重复、项目表与现有 Project Control 重复。
7. 当前部署树把 `backups/` 放在 live memory root 内，与“备份目录必须位于 live root 外”矛盾，必须改。

| 项目 | 建议 |

### 1.2 能否开始 P0

可以，但条件是：

- P0 仍然只做文档、接口合同、临时 fixture 和只读核验；
- 不触碰 Stable live data；
- 不创建真实个人记忆；
- 不安装或承诺 SQLCipher/向量/图依赖；
- 不新建第二套项目身份；
- 不把“默认建议”解释成 Cyrus 已授权执行具体动作。

## 2. 本轮修订做对了什么

### 2.1 上一轮十个核心升级已经落地

修订稿已经明确吸收：

- G/M 治理面与记忆面分离；
- 稳定 project identity；
- Global/Private/Project 分片；
- candidate 与 canonical 写入隔离；
- 简单任务跳过记忆；
- FTS5 baseline；
- `systemPrompt.context` 不再承载任务记忆；
- Online Backup API；
- 来源可用性与 portable locator；
- 用户删除、导出、纠正和暂停能力；
- 向量与图必须通过相对 FTS 的评测；
- effective prompt 默认只输出 manifest；
- 压缩后从权威源重建，而非“永不压缩”。

这些改动是正确的，尤其以下四点非常关键：

1. **不再让每轮自动召回污染历史。**
2. **不再把向量 BLOB 误认为近邻索引。**
3. **不再运行中直接 copy WAL 主库。**
4. **不再允许 LLM 直接写 canonical memory。**

### 2.2 实施顺序显著改善

P0–P6 的新顺序合理：

```text
合同/身份/安全
  → 最小 SQLite + FTS + 显式工具
  → 渐进披露
  → candidate 提取
  → 可选向量
  → 可选图
  → 多项目与稳定版
```

这个顺序比先 vendor 图内核、自动提取和 embedding 安全得多，也更容易定位问题。

### 2.3 对 Codex 评审的保留意见基本合理

DeepSeek 没有把“Codex 可观察结构”冒充成闭源内部事实；也没有机械照抄所有建议，而是：

- 保留 L0–L4 作为内容归属轴；
- 使用 G/M 作为实现轴；
- 把 20/100/20 万定位为压力上限而非强制目标；
- 承认 SQLCipher Windows/Electron 原生构建需要先验证；
- 将 HMAC 放在后续硬化，而不是阻塞最小版本。

这些判断是成熟的。

## 3. 拍板前仍需修正的架构问题

### 3.1 不要再建第二套项目注册表

修订稿写“优先复用 Project Control，若没有则记忆控制面新建 registry”。但当前仓库不仅有规范，Project Control 的迁移和实现已经存在稳定项目身份：

- `docs/PROJECT_CONTROL_DATA_MODEL.md:15`：两个入口最终获得同一种稳定 `project_id`；
- `docs/PROJECT_CONTROL_DATA_MODEL.md:46`：路径、文件夹名和 Git remote 只能用于发现，不能当 ID；
- `docs/PROJECT_CONTROL_DATA_MODEL.md:112`：`projectId` 创建后不可修改或复用；
- `plugins/project-control/migrations/0001_core_control_plane.sql:9-31`：已存在严格 `projects` 表；
- 同一 migration 的 `workspace_locations` 已保存项目与活动路径关系。

因此应定案：

> 记忆系统不得创建另一套 `projects/project_uuid` 身份源；必须把 Project Control 的 `project_id` 作为唯一项目身份。

记忆 `catalog.sqlite3` 只保存：

- Project Control `project_id` 的引用；
- memory shard locator；
- memory policy；
- sensitivity/retention；
- 最近同步 revision；

不重复保存项目名称、root aliases 和 lifecycle 的 canonical 值。需要展示时通过 Project Control Host API 读取或维护明确标记为 cache 的投影。

### 3.2 决策 6 的三个选项都不是最终正确方案

“固定 Personal 根”“按当前文件夹”“依赖 Git”都只能辅助发现，不能作为项目身份。

推荐新增选项 D：

```text
Project Control project_id 是身份
  + 当前 Session 与 project_id 显式绑定
  + launcher/Project Control 传 workspaceRoot/locationRef
  + managed 项目通过 project.yaml marker 验证
  + Personal 默认根只作未选择项目时的安全 fallback
```

身份不明时：

- 允许只读检查；
- 禁止长期写入；
- 禁止跨项目召回；
- 提示选择/注册项目。

### 3.3 `scope_kind` 与 `status` 仍然混用

当前 Schema 同时存在：

- `scope_kind=candidate`；
- `status=candidate`。

candidate 是生命周期状态，不是作用域。否则一条候选到底属于哪个项目会变得模糊。

建议：

```text
scope_kind = global_user | portfolio | project | workspace
status     = candidate | active | disputed | superseded | archived
```

自动候选仍保存目标 `project_id/workspace_id`，只是 `status=candidate`。

`session` 也不建议进入长期 claims scope；如果只是会话暂存，应存在独立 inbox/staging 或上游 Session 中，确认后再转入长期 scope。

### 3.4 `confirmed` 与 `active` 状态重复

当前状态机：

```text
candidate → confirmed → active → disputed → ...
```

但文档又称 M1 为 Confirmed，并把 confirmed 和 active 都作为默认召回候选，没有定义何时从 confirmed 变 active。

推荐拆成两个正交维度：

```text
lifecycle_status = candidate | active | disputed | superseded | archived
authority_class  = user_confirmed | repo_verified | machine_observed | llm_extracted
```

当 candidate 获用户确认时，直接变成 `active + user_confirmed`；不需要中间 confirmed 状态。

### 3.5 复合唯一键在 `scope_id=NULL` 时不会去重

SQLite UNIQUE 允许多个 NULL。当前：

```sql
UNIQUE(scope_kind, scope_id, kind, normalized_content_hash)
```

如果 `global_user` 的 `scope_id` 是 NULL，同一内容可以重复插入多次。

建议之一：

- `scope_id TEXT NOT NULL`，Global 使用固定 id，例如 `global:cyrus`；或
- 使用 expression unique index：`COALESCE(scope_id, '')`。

优先推荐第一种，语义更清晰。

### 3.6 candidate TTL 删除会被外键阻止

当前 `candidate_idempotency.claim_id REFERENCES claims(id)` 没有 `ON DELETE`，同时文档要求 candidate 到期后 DELETE、幂等键继续保留。

这两条不能同时成立：默认外键会阻止删除 claim。

建议：

```sql
claim_id TEXT REFERENCES claims(id) ON DELETE SET NULL
```

并在幂等表保留：

- idempotency_key；
- original_claim_hash；
- outcome（expired/rejected/promoted）；
- expires_at；

或者 candidate 到期后先改状态为 rejected/expired，再按独立清理策略物理删除。

### 3.7 删除语义和外键 cascade 尚未闭合

物理删除 claim 时，以下表都会受影响：

- FTS；
- embeddings；
- claim_evidence；
- claim_relations；
- recall_items；
- candidate_idempotency；
- superseded_by 自引用。

必须逐表定义：

- `ON DELETE CASCADE`；
- `ON DELETE SET NULL`；
- 保留不可逆 tombstone；
- 或禁止物理删除、改用 crypto-shred。

不能只写“live+索引即时删除”而不定义事务顺序。

### 3.8 catalog 的 JSON 路径字段不应成为新事实源

修订稿的 `projects` 表仍用 JSON 保存 aliases/root_aliases，并带 `shard_path`。如果保留 catalog，建议：

- 不复制 Project Control canonical metadata；
- `shard_path` 使用相对 locator，不写绝对路径主键；
- 如果必须 cache 项目显示信息，增加 `source_revision` 和 `is_cache=1`；
- catalog 同样包含敏感项目名和路径，不能认为“没有正文就不需要加密”。

### 3.9 Global shared 与 Private 的归属需要再明确

`global_user` 是个人偏好，本质仍属于用户隐私。它不应默认进入名为 `shared.sqlite3` 的普通全局库。

建议：

- `private/user.sqlite3`：用户偏好、个人信息、跨项目但属于 Cyrus 本人的信息；
- `global/patterns.sqlite3`：经过确认的非敏感跨项目方法和 pattern；
- System/AGENTS 的规则正文仍不复制进数据库。

这样“跨项目可用”不会被误解成“低敏感或可分享”。

### 3.10 备份目录示意与规则矛盾

第 9.12 节画的是：

```text
<数据根>/memory/backups/
```

第 9.9.4 节又规定“备份目录必须在 live root 之外”。两者冲突。

建议改成：

```text
<数据根>/memory-live/
<数据根>/memory-snapshots/
<另一物理设备>/memory-offline/
```

live、同机 snapshot、异机/offline 三类必须有不同故障域标签。

### 3.11 加密排到 P6 太晚

修订稿一方面说稳定版前加密，另一方面 P6 才写“加密落地”。如果 P1–P3 已经允许真实显式记忆、项目业务信息或个人偏好进入明文 Dev DB，就已经形成迁移和泄漏风险。

建议：

- P0：定威胁模型、key contract、storage abstraction；
- P1：用 fixture 完成加密实现 spike 和 backup encryption；
- P1–P2：只允许合成数据；
- 第一次写真实 Personal/商业记忆之前：live DB 加密必须完成；
- SQLCipher 失败时，明文 + ACL 只能继续用于合成/非敏感 fixture，不能作为 Stable 的长期回退；
- 如果最终只依赖 BitLocker/ACL，必须由 Cyrus 明确认可其威胁边界，而不是静默降级。

### 3.12 “15 项全部清零才能 P0”过度增加用户负担

P0 的职责之一正是把技术未知转化为有证据的选择。以下事项不需要 Cyrus 现在决定具体实现：

- 注入 seam 的内部 API；
- FTS trigger 的实现方式；
- Project Control schema 是否可复用（现已核验可复用）；
- SQLCipher 具体库；
- 向量和图是否最终上线；
- 精确性能阈值。

Cyrus 应现在拍板的是：

- 哪些数据允许记；
- 哪些风险不可接受；
- 备份和密钥偏好；
- System 红线；
- 是否建立本地 Git；
- 是否允许 Dev AGENTS 投影；
- 加密是否是写真实数据的硬门槛。

其余可以按安全默认进入 P0 调研，P0 用证据再回来提案。

## 5. 逐项拍板建议

## 决策 1：备份频率、RPO、RTO

### 建议答案

选择 **A+**：

- 每日做一次完整、经过 `integrity_check` 的在线一致性快照；
- 大升级、schema migration、批量导入、批量删除前立即做一次；
- 用户确认一批高价值记忆、完成重要 promotion 后，可触发一次有节流的增量/快照任务；
- 普通 RPO 不超过 24 小时；
- 危险变更前 RPO=0，且快照后要暂停相关 writer，避免“备份完又写入”；
- 单项目 RTO 不超过 2 小时；
- 每季度真实恢复演练一次。

### 理由

仅按固定时间每天一次已经够做基础保护；对关键决策和迁移采用事件触发，可以避免为了把 RPO 从 24h 降到 6h而制造大量无意义全量快照。

### 建议保留期

- 每日 14 份；
- 每周 8 份；
- 每月 12 份；
- 迁移前快照保留到验收后至少 30 天；
- 项目归档包按项目生命周期保留。

具体磁盘成本在 P0 用合成规模测算后再确认。

---

## 决策 2：异物理位置备份

### 建议答案

选择 **B，但修改同步语义**：

- 使用真正不同的物理设备；
- 只写加密、版本化、带 manifest 的 snapshot；
- 不做删除同步、不做 mirror、不覆盖唯一旧备份；
- 移动盘插入后可以提示“发现已授权备份盘，是否同步”，或者由 Cyrus 给某个固定设备/目录一次性 standing authorization；
- standing authorization 必须限定设备标识、目标根、数据等级、保留期和停止开关；
- 云端 C 暂不启用。

### 为什么不建议“插上自动镜像”

镜像会把源端损坏、误删或勒索软件加密结果迅速传播到备份。版本化 snapshot 才能回到事故前状态。

### 敏感项目

- Internal：允许进入加密移动盘；
- Sensitive：需要项目级 allowlist；
- Restricted：正文不进记忆库，因此不应进入普通备份；
- 云端：未来单独审批，并且只上传客户端已加密包。

## 决策 3：恢复密钥

### 建议答案

选择 **A 的强化版**：

- 使用经过审计的密码学库生成 256-bit 随机恢复秘密；
- 如果转成助记词，使用明确、标准、带校验的编码，不要由模型自己随机挑 12–24 个词；
- 建议 24 词或等价高熵 recovery code；
- 两份纸质副本放在两个不同安全位置；
- 如果 Cyrus 已经稳定使用密码管理器，可再存一个加密副本，但密码管理器不能是唯一副本；
- 每年或重大迁移前做一次“只用恢复密钥解开测试备份”的演练。

### 密钥轮换

区分：

- 纸张丢失但未确认泄露：生成新 recovery wrapping key，重新包裹 data key；
- recovery secret 可能泄露：立即重包裹所有分片 data key，必要时轮换 data key；
- data key 泄露：需要重加密对应分片。

不能笼统写“旧钥匙作废，数据不受影响”，必须根据泄露的是哪一级密钥处理。

## 决策 9：`经验.md` 与数据库

### 建议答案

选择 **A'：保留人类可读 Markdown，但只能单向生成，禁止双向同步。**

### 推荐迁移阶段

#### 过渡期

```text
经验.md = canonical source
数据库 = 从 MD 导入的可重建索引
```

- MD 仍可人工编辑；
- DB 导入记录 source hash；
- DB 不反写 MD；
- 导入幂等；
- 原 MD 保留历史快照。

#### 记忆系统成熟后

```text
数据库 confirmed claims = canonical source
经验.md = 自动生成、只读的人类视图/索引
```

- 文件头明确写“GENERATED，勿手改”；
- 用户修改通过 memory.correct 或结构化编辑入口；
- 重新生成 MD；
- Git 可跟踪非敏感生成视图，但 Private/Sensitive 内容不导出进仓库 MD。

### 为什么拒绝双向同步

双向同步会遇到：

- 同时编辑冲突；
- 内容拆分/合并映射困难；
- 删除语义不一致；
- 敏感内容误导出；
- source of truth 不明确；
- 自动合并把旧内容复活。

## 决策 11：机器门禁优先级

### 建议答案

3. secret/PII/Restricted 写入 Gate；

#### Wave 4：构建与发布

6. revision、hash、制品、文档、兼容性和发布 Gate。

每一波仍需在实施前单独申请具体授权，不把本次架构拍板理解成代码修改授权。

## 10. 最终建议

这次 v2 已经值得继续推进，但最重要的不是让 Cyrus 在 15 个技术选项里做完全部工程设计，而是把 Cyrus 的角色保持在正确层面：

- DeepSeek 再把技术证据转成少量真正需要 Cyrus 选择的 trade-off；
- 没有真实 trade-off 的 Schema、外键、FTS、路径解析问题，应由工程验证解决，不应转嫁给用户拍板。

因此我的总体建议是：

> 批准 v2 方向；按本文修订 15 项；先完成 P0 合同和 Schema 修正；真实数据、Stable、Git、System、AGENTS 投影和机器 Gate 仍逐项授权。
