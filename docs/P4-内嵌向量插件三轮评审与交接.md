## 二、第一次评审：架构方案

### 2.1 成立的部分

1. 不用 Ollama、无端口、无独立服务、运行时不联网，符合本项目的零感知与隐私目标。
2. 使用 `@huggingface/transformers` 处理 tokenizer、pooling 和 normalization，比手写推理合同可靠。
3. ONNX 权重放在 `F:\AI`，不并入 Git 和普通发布包，避免每次客户端升级重复分发约 587 MB 模型。
4. SQLite 只保存可重建的派生向量，模型或预处理合同变化时用新 generation 重嵌，方向正确。

### 2.2 必须修改的五点

#### A. CPU 默认，DirectML 只作可选实验

本机为 i7-13700K、64 GB RAM、RTX 4090 24 GB。DirectML 可以成功加载三款模型，但短文本和 batch 16 都比 CPU 慢：

| 模型 | CPU 单句中位 | DirectML 单句中位 | CPU batch 16 | DirectML batch 16 |
|---|---:|---:|---:|---:|
| bge-m3 INT8 | 15.3 ms | 140.0 ms | 93.1 ms | 207.1 ms |
| Qwen3-0.6B INT8 | 33.9 ms | 277.2 ms | 356.4 ms | 462.5 ms |
| gte-multilingual-base INT8 | 9.9 ms | 67.9 ms | 73.6 ms | 128.1 ms |

因此正式策略应为：`executionProvider=cpu` 默认；只有目标机器、目标文本长度和目标 batch 的实测证明 DML 更快时才允许开启。不要在每次请求上探测 GPU；插件启动后固定一个已经验证的 provider。

#### B. 推理放 worker thread，不堵 Harness Host 事件循环

“进程内”不等于“主线程内”。建议插件用一个 `worker_threads` worker 持有 tokenizer 与 ONNX session：仍是单个 DSH 进程、无端口、无外部服务，但不会让 batch 重嵌阻塞 Host 的 HTTP、会话事件和退出流程。

需要：单飞初始化、队列上限、AbortSignal、关闭时 drain/terminate、队列满时显式 `busy`，不能无限堆积。

#### C. 懒加载与空闲释放

CPU 加载后的 RSS 增量：bge-m3 约 881.8 MiB、Qwen3 约 773.5 MiB、gte 约 657.4 MiB。不要随 DSH 启动常驻加载；第一次真实需要语义检索或 backfill 时再加载。可选空闲释放必须有明确状态机，不能在请求中途卸载。

#### D. 插件接口不能只有 `embed(texts[])`

建议合同：

```ts
embed({
  texts,
  purpose: 'query' | 'document',
  generation,
  signal,
}): Promise<{
  vectors: Float32Array,
  count: number,
  dimensions: number,
  generation: string,
}>
```

- `purpose` 决定 query instruction；Qwen3/gte 查询侧需要前缀，文档侧不加。
- 返回扁平 `Float32Array`，避免 `number[][]` 带来的对象开销和多次复制。
- generation 必须绑定模型、ONNX 哈希、tokenizer 哈希、dtype、pooling、normalization、query instruction 版本、最大长度与 runtime 版本。

#### E. 禁止自动下载与静默远程回退

正式运行时设置 `env.allowRemoteModels=false`，只接受通过 manifest 和 SHA-256 的本地目录。模型缺失或损坏时状态为 `semantic_unavailable`，继续 FTS；不得现场联网下载，也不得切到远程 embedding。

## 三、第二次评审：模型、许可与本地实测

### 3.1 公开资料能说明什么

- [Qwen3-Embedding-0.6B 官方模型卡](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B)声明 Apache-2.0、100+ 语言、32K 上下文、最高 1024 维，并要求 query instruction + last-token pooling。其发布表中，多语言 MTEB Mean(Task) 为 64.33、Retrieval 为 64.64；同表 bge-m3 分别为 59.56、54.60。这个结果说明 Qwen3 是合理的“更好模型”候选，但属于通用公开基准，不等于 DSH 记忆召回结果。
- [BGE-M3 官方模型卡](https://huggingface.co/BAAI/bge-m3)声明 MIT、1024 维、8192 token，并同时训练 dense/sparse/ColBERT。当前插件只使用 dense CLS 向量，不能把它的多向量与稀疏能力算作已获得收益。
- [gte-multilingual-base 官方模型卡](https://huggingface.co/Alibaba-NLP/gte-multilingual-base)声明 Apache-2.0、305M 参数、768 维、8192 token。它体积和 CPU 延迟最低，但 Transformers.js 加载时需要对 `model_type=new` 走 EncoderOnly fallback，维护确定性弱于 bge-m3。
- [Transformers.js Node 文档](https://huggingface.co/docs/transformers.js/en/tutorials/node)支持本地模型目录并允许关闭远程模型；[onnxruntime-node 当前平台表](https://www.npmjs.com/package/onnxruntime-node)说明 Windows x64 预构建包支持 CPU 与 DirectML。DirectML 官方文档同时说明它已进入持续维护阶段，Windows 新开发重点转向 WinML；本项目不应把 DML 当成默认必经路径。

### 3.2 下载与版本锁定

| 角色 | 模型目录 | ONNX 大小 | 许可 | 固定 revision |
|---|---|---:|---|---|
| 正式推荐 | `F:\AI\bge-m3-onnx` | 569,694,530 B | MIT | `Xenova/bge-m3@4de1325...` |
| 质量挑战者 | `F:\AI\qwen3-embedding-0.6b-onnx` | 613,527,631 B | Apache-2.0 | `onnx-community/Qwen3-Embedding-0.6B-ONNX@c25a394...` |
| 效率对照 | `F:\AI\embedding-eval\gte-multilingual-base-onnx` | 340,318,797 B | Apache-2.0 | `onnx-community/gte-multilingual-base@2edbf5e...` |

每个目录都有 ONNX、tokenizer、config、README、上游 README、标准许可文本和 `MODEL_MANIFEST.json`。主文件 SHA-256：

- bge-m3：`0826f8c1ab9edf1801db86c61919d4d108e8bfc0b809ec823ad366882ff0b77d`
- Qwen3：`87cd124e0ef1fd1f223ebc283efccbaeac386d0b08344701c46975d0657b591f`
- gte：`ab2bd164ebd8ca9003dc49a981b611e849b5d326f504c8873ba76e07fa6c0082`

### 3.3 本地离线检索结果

测试集是 12 条非敏感、项目化记忆和 12 个查询，覆盖中文改写、工程术语、跨语言、路径/身份、规则/事故、候选治理和离题干扰。它适合做模型 spike，不足以代替 P4 最终 helpful-hit 回归集。

| 模型（CPU/INT8） | 加载 | 单句中位 | batch 16 | Top-1 | Recall@3 | MRR |
|---|---:|---:|---:|---:|---:|---:|
| bge-m3 | 1,215.1 ms | 15.3 ms | 93.1 ms | 11/12 = 91.67% | 100% | 0.9444 |
| Qwen3-Embedding-0.6B | 1,024.9 ms | 33.9 ms | 356.4 ms | 10/12 = 83.33% | 91.67% | 0.8750 |
| gte-multilingual-base | 789.5 ms | 9.9 ms | 73.6 ms | 7/12 = 58.33% | 75.00% | 0.7250 |

结论：**有通用公开基准上优于 bge-m3 的 Qwen3-Embedding-0.6B，但当前没有证据证明它更适合本项目。主模型保留 bge-m3。** Qwen3 权重已下载，等真实回归集扩充后可无网络复测。

### 3.4 原方案的固定余弦阈值必须删除

原方案规定“同义 > 0.8、无关 < 0.5、跨语言 > 0.7”。本次结果证明不同模型的分数分布不可横比：

- bge-m3 的同义对为 0.7212，低于原通过线，但检索 Top-1 是 11/12。
- gte 的无关对为 0.7287，高于原失败线，说明它整体分布偏高。
- 三款模型对“必须跑测试”与“可以跳过测试”这组反义/否定句都给出较高相似度（0.7068–0.9404）。embedding 不是事实判断器或否定检测器。

模型门改用：Top-1、Recall@k、MRR、同义相对无关的 margin、hard-negative 错误类型、延迟、内存与离线可用性。不同模型不得用同一个绝对余弦阈值拍板。

## 四、第三次评审：正式实现与上线门

### 4.1 召回融合必须从“FTS 后 rerank”改为“候选并集后融合”

如果只对 FTS top-k 做向量 rerank，FTS 因字面不匹配漏掉的记忆永远回不来，等于没有解决 P4 的原始问题。

建议流程：

```text
需求门
  -> scope/status/authority 硬过滤
  -> FTS top-k
  -> 同一小候选域内 vector top-k（当前 <=64 可 brute-force）
  -> 两路候选并集
  -> RRF/名次融合 + 精确 ID/路径/关键词加权
  -> 冲突、来源、新鲜度、项目身份与预算门
  -> 最终少量召回包
```

优先用 Reciprocal Rank Fusion 或经过回归集校准的名次融合，不直接混加 FTS 分数与 cosine；两种分数不在同一量纲，模型之间的 cosine 分布也不同。

### 4.2 写入与回填

1. claim 事务提交后再异步 embedding，绝不把模型推理放进 SQLite 写事务。
2. 状态至少区分 `pending | ready | failed | stale`；失败记录错误码和重试次数，不记录正文。
3. 单条写入可小批次合并；全量 backfill 分批、可取消、有进度、有最大重试和 FTS 降级。
4. query embedding 可按 canonical query + generation 做小型 TTL/LRU 缓存；document embedding 以 `content_hash + generation` 幂等。

### 4.3 generation 与存储合同

generation 不能只包含模型名和维度。建议主键材料：

```text
model repo + revision
+ ONNX SHA-256
+ tokenizer SHA-256
+ dtype
+ pooling
+ L2 normalization
+ query instruction version
+ max input/truncation policy
+ transformers.js/onnxruntime-node compatibility version
```

存储先用 Float32 BLOB：1024 维每条 4096 B，本项目数百条规模没有必要先引入向量量化。读取时校验字节长度、有限数值和近似单位范数；坏向量标 failed 并重建。

### 4.4 依赖与封装风险

- spike 固定 `@huggingface/transformers@4.2.0`，其精确依赖 `onnxruntime-node@1.24.3`。正式代码不要再声明一个不一致的 ORT 版本，避免双份 native runtime 和 provider 行为漂移。
- 当前 `onnxruntime-node` 安装包含多平台文件；Windows x64 子集约 59.3 MiB，其中 DirectML/dxcompiler/dxil 约 36.3 MiB。既然 CPU 是默认，正式打包前应验证能否只带 win32-x64 CPU 所需文件；任何裁剪都必须用 packaged Electron smoke 证明，不能凭猜测删 DLL。
- pnpm 11 已提示根 `package.json` 下的 `pnpm.onlyBuiltDependencies` 不再读取。正式引入时要把 `onnxruntime-node`/`sharp` 的构建许可放进仓库当前使用的 `pnpm-workspace.yaml allowBuilds`，再做一次空缓存 clean install。
- 必须验证 Electron 43 打包目录、Portable、NSIS 三种形态的 native binding、模型外置路径、应用关闭和无残留进程。

### 4.5 P4 两道不同的门

1. **模型门**：本轮已通过——bge-m3 可完全离线加载，质量与延迟在三个候选中最适合当前项目。
2. **功能门**：尚未通过——正式实现后，必须在覆盖驱动的真实脱敏回归集上比较 FTS-only 与 Hybrid。只有 helpful hit 提升、cross-project leak 仍为 0、错误/延迟/内存可接受，才保留向量通道。

不要用本轮 12 题替代功能门，也不要为追求固定题数牺牲覆盖。回归集至少覆盖：低字面重合、缩写/别名、中英混合、代码/路径、否定与反义、旧事实/冲突、prompt injection、跨项目同词异义、无需历史的任务。
