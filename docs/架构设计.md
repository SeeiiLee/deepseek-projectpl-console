# DeepSeek Harness Personal 架构设计（跨 Session 权威参考）

> 本文定位：**架构职责、边界、接缝（seam）目录与演进规则**的唯一权威。
> 行为规则见 WORKING_RULES_AND_PITFALLS.md，跨项目方法沉淀见 WORK_RULES_AND_PITFALLS.md，本仓库技术坑见 经验.md，产品/协议合同见 PROJECT_CONTROL_SPEC.md 与 PROJECT_PROTOCOL.md。本文只链接、不复制这些规则。

## 1. 设计目标（影响架构的最高原则）

1. **保护优先**：人、数据、凭据、稳定版 大于 速度/便利/功能数量。架构体现：隔离身份、受保护路径强制拦截、显式失败、凭据不可回读。
2. **分层归责**：Electron Main 只做壳（窗口/托盘/快捷方式/更新/进程树），不承载业务状态；Harness Host 做能力与事实（文件/SQLite/凭据/PTY/安全/受限 HTTP）；Client 只消费受限 API。任何一层越界 = 架构债。
3. **一个事实一个来源**：每类事实只有一个权威归属；其他位置只存引用/哈希/投影，不得反向覆盖权威（见第 4 节）。
4. **显式失败优于静默降级**：默认值、兜底、空 catch、缓存写而不读都是最贵 bug 类。宁可空态诚实，不可假数据填满。
5. **简单、稳定、boring**：能 50 行不用 200 行；不为臆想需求提前建抽象；Surgical Changes（每行改动可追溯到需求）。
6. **跨插件只走 seam**：service / slot / typed intent；禁止跨插件导入实现符号（客户端 bundle 有纯度门禁强制）。
7. **稳定/测试/开发全隔离**：AppId、userData、DSH_HOME、数据库、单实例锁各自独立；自动化永不碰稳定版路径。
8. **可验证完成**：合同（contract/schema）+ 测试 + 真机证据，三者缺一不算完成。

## 2. 总体分层

```text
Electron Main（src/main.js + desktop-bridge + harness-process）
  窗口/托盘/快捷方式/目录选择票据/更新/进程树监督；无业务状态
        │ 监督（spawn + Job Object + PID 树）
        ▼
Harness Helper（上游 rc.5，只读）runProfile(web) + 官方 shutdown
  会话/聊天/模型/工具 = 官方实现；Personal 插件经 cordis overlay 激活；
  loopback 随机端口，精确 origin 判定
        │                     │
        ▼ Host 半             ▼ Client 半
  15 个 @cyrus/dsh-* 插件      slots（shell.overlay / settings.section /
  webServer routes / 服务       project.control / workbench.panel）
  SQLite 单写者 / 凭据引用     workbench viewers + typed intents
  / PTY / 文件事务 / Outbox
        ▼
存储面：Project Control SQLite（唯一写者）· credentials 引用
  · 上游 Session 存储 · 工作区文件（DB 只存引用/哈希）· F: 数据
```

- **数据流**：Renderer → 受限 HTTP（自定义 client header + DTO）→ Host 插件 → 单写者存储；事件经 Outbox → dispatcher → managed 项目文件（事务后重试副作用）。
- **命令流**（Project Control 全系）：envelope → Host 验证（schema/权限/版本/大小/引用）→ expectedRevision 乐观并发 → Receipt + Domain Event + Outbox 同事务 → 事务后适配器。网络/文件/第三方调用永不进 SQLite 写事务。

## 3. 插件系统架构

### 3.1 上架一处新插件 = 四处必改（漏一处冒烟即红）

1. plugins/<name>/：package.json + tsconfig.json + tsdown.config.ts + 源码 + 测试；
2. src/personal-plugins.js 的 PERSONAL_PLUGINS（junction 链接清单）；
3. plugins/cordis.patch.yml（桌面 overlay 的激活清单——只建 junction 不激活 = 冒烟 missingEntries）；
4. 插件自己的 test/（含 structure 测试：声明边界、seam 用法、CSS 局部性）。

### 3.2 现存 seam 目录（新功能只能从这里接入）

- Host service：webServer（受限 HTTP 路由，effect + disposer）；credentials（set/unset/describe 给 UI，resolve 仅 Host 获权适配器）；sessions / subprocess / loader。
- Client slot：shell.overlay（聊天旁浮动 dock，多条目 id+order）；settings.section（设置页板块）；project.control（项目面板唯一占有者，single/root）；workbench.panel（Workbench 唯一根，single/root）。
- Typed intent：workbench.open({family, viewerId, resourceKey})——打开/聚焦查看器，不重实现查看器。
- Viewer 注册：workbench.viewers.register({family, canRestore, render})——插件自有有界视图。
- 代表消费者：终端 dock 与识图 dock（shell.overlay）；connection-center/theme/usage-balance（settings.section）；project-control（project.control）；workspace-* 查看器（viewers + intents）。

### 3.3 插件纪律（上游 capability seam 的完整角色）

- 注册即 effect：每个注册都有 disposer；HMR/卸载必须清理 route、timer、service、PTY、资源。
- 服务三件套完整：Service Definition + Provider + Consumer 齐备才算能力完成；optional service 用 ctx.get(name)，声明注入才用 ctx.<name>。
- 禁止：跨插件实现符号导入（type-only + 环境声明 shim 可以；Host 侧运行时 peer 用 apply 内动态 import）；模块级 store 单例；全局 DOM/CSS patch；第二套 Terminal/Details/Review/状态源。
- 包边界：Host 半（node）与 Client 半（browser bundle）分开构建；客户端 bundle 纯度门禁自动拦截越界值导入。---

## 4. 数据与状态架构（一个事实一个来源）

- 协议/ID/状态语义 → 版本化 Project Protocol + 机器 Schema；其他位置只引用 schema 版本。
- managed 项目身份/文档映射 → .dsh-project/project.yaml；数据库镜像 + 哈希复验。
- legacy 身份/绑定 → Project Control 全局 SQLite。
- 本机路径与位置历史 → workspace_locations；路径票据短期引用。
- WorkItem/Run/Review/Decision → 全局库当前状态表；只读投影。
- 会话正文/工具调用 → 上游 Session 存储。
- Artifact 正文 → 工作区文件/受控外部对象；DB 只存引用+版本+哈希。
- 凭据值 → 系统凭据库（Connection Center）；DB/事件只存不可回读的 credential ref。
- 卡片/搜索/最近活动 → 可重建投影，不作为新事实源。

### 4.1 不可动摇的存储铁律

1. 单写者：SQLite 只有一个 Host 写者；其他 Harness/Client/Agent 一律走版本化 Host API。
2. 事件流 append-only：UNIQUE(aggregate_type, aggregate_id, aggregate_revision)、command_id UNIQUE（一命令一事件）；事件 revision 与行 revision 同源（见 经验.md 三、事件流铁律），防止 UNIQUE 撞车。
3. 命令幂等：同作用域 + 同 key + 同哈希 → 返回原 Receipt；同 key 不同哈希 → 拒绝。
4. 文件事务顺序：先 staging（exclusive create + 哈希核对）→ 目标 absent 复验（防 TOCTOU）→ rename → 重读复验 → 才提交 DB；DB 失败只回滚本计划创建的文件。
5. Quarantine 是证据不是垃圾：拒绝/隔离保存最小诊断 + 引用 + 哈希；修复 = 新命令，不篡改原记录。
6. 凭据不可回读：describe（UI 脱敏状态）与 resolve（Host 消费）分离；日志/事件/Receipt 白名单脱敏。

## 5. 安全架构

- 回环绑定：Harness 只绑定 127.0.0.1 随机端口；readiness 只接受精确 http://127.0.0.1:<port>（拒绝 127.1、十进制/十六进制回环、空白、credentials、路径、非 HTTP）。
- Renderer 沙箱：nodeIntegration:false、contextIsolation:true、sandbox；导航/新窗口/权限严格白名单。
- 路径票据：Renderer 永不提交裸绝对路径；系统选择器签发短期/单次/绑定用途票据，Host 解析并做 lstat+realpath containment（symlink/junction 逃逸拒绝）。
- 有界输入：所有输入有深度/字符串/数组/字节/条目/时间上限；限额作用于包含包装的完整结果；DTO 不带 ORM 对象、凭据、完整会话或正文。
- 盘符不等于本地磁盘：关键数据只落已知本地固定盘；拒绝系统根/UNC/未知网络盘。

## 6. 隔离架构（稳定 / 测试 / 开发）

- 进程/AppId：稳定版 DeepSeek Harness Personal / com.cyrus.deepseek-harness-personal；测试版为 … Dev / …-dev；开发态为目录运行。
- userData：稳定版 F:\documents\Cyrus Deepseek Harness Data；测试版与开发态各自独立。
- DSH_HOME：稳定版同数据目录 harness-home；测试版/开发态独立或临时。
- 项目库与单实例锁：三者各自独立。

- 自动化纪律：packed smoke 只启动 *-Smoke.exe 改名副本；进程清理只按 PID + 明确标记（scripts/kill-smoke-orphans.js）；受保护路径（安装目录、F: 数据主目录、遗留备份目录）由 scripts/protected-paths.js 强制拦截。详见 经验.md 与 WORKING_RULES_AND_PITFALLS.md 第 11 节。
- 发布节奏（固定顺序）：开发树实现 → 合同/测试/构建门禁 → 开发态 smoke → 测试版打包 + packed smoke → Cyrus 在测试版真实验收 → 双版本托盘完全退出 → 稳定版打包 + 发布预检 + 实物哈希 → Cyrus 批准 → 安装/发布 → 真实聊天/关闭/数据位置/回滚/无残留验证。

## 7. 新功能接入决策树（架构应该怎么长）

任何新需求，按顺序回答：

1. 它是状态事实吗？→ 归 Project Control：先定权威来源（第 4 节）→ 协议/迁移 → 命令/事件 → 投影/UI。禁止就地造第二个状态源。
2. 它是资源查看/操作吗？→ 归 Workbench：Host remote（路径票据 + containment）→ viewer 注册 → typed intent 入口。禁止绕过票据直读文件。
3. 它是会话内交互吗？→ shell.overlay dock 或官方链路；若官方不支持（如图片消息），走 Host 桥接 + 结果回填，不做会话日志手术。
4. 它是配置吗？→ 归 Connection Center / 相应设置 slot；凭据只写引用。
5. 放哪层：Main 只做壳能力；业务事实永远在 Host；Client 只呈现。
6. 能否用现有 seam？能 → 用；不能 → 停下仲裁（不得为解锁自己新增 export/绕过）。
7. 按变更面选验证（WORKING_RULES_AND_PITFALLS.md 第 12 节矩阵）：纯函数→单测；存储/事务→单测+篡改/幂等/revision/崩溃回滚；插件→check:plugins；桌面→smoke；打包→packed smoke；发布→预检+实物哈希+Cyrus 批准。

### 7.1 变更方法路由（每类变更的强制流程）

- 新功能/改行为 → TDD：红→绿→重构，垂直切片，测行为不测实现。
- Bug → Debug：先写可复现测试再修；修复带回归测试。
- 高风险（迁移/认证/不可逆/API/费钱）→ Doubt：fresh-context 子 Agent 对抗性审查，最多 3 轮后上报 Cyrus。
- 合并前 → Review：五轴（正确/可读/架构/安全/性能）。
- 臃肿 → Simplify：精确保持行为；清晰大于聪明。
- 多文件/大变更 → Incremental：每切片一件事、可编译、测试绿、可回滚。---

## 8. 架构红线清单（违反 = 事故）

1. 稳定版路径（安装目录 / F: 数据主目录 / 遗留备份目录）自动化零写入零删除。
2. 进程清理只按 PID；禁止按名批量杀；引用受保护路径的进程一律跳过。
3. 上游 D:\Deepseek Harness 只读；Personal 能力只在 Personal 实现。
4. 跨插件只走 seam；客户端 bundle 纯度门禁不可绕过。
5. SQLite 单写者；网络/文件/第三方调用不进写事务。
6. 事件流 revision 同源、append-only、一命令一事件。
7. 凭据不进入 DB/事件/日志/发布物；Renderer 只见脱敏状态。
8. 不建立第二套 Terminal/Details/Review/状态源；Markdown 写 done 不等于状态变更。
9. 未获具体授权：不 commit/push/发布/安装/覆盖稳定版/迁移/付费调用/删除/系统配置。
10. 文档不写推理链、凭据、个人原始数据；易变数字不长期手抄。
