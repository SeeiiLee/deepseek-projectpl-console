## 0. 结论先行

1. **治理的基本单位是「4+1 变更域」**：客户端、插件、模型资产、上游 seam，外加贯穿四者的用户数据迁移。所有未来架构升级产生的问题，都可以归类为变更域之间的兼容问题；治理制度围绕「让每类变更可分类、可授权、可回滚、可追溯」建立。
2. **提前做七件事**：ADR 决策档案、权威文档制度、机器可读兼容矩阵、seam 契约测试、上游观察例行化、变更分级授权、发布总账。这七件事全是轻量文档/配置制度，不是代码工程，现在就能做，做了之后未来每一次架构调整的成本都减半。
3. **开发侧用「四层门禁 + 清单即合同」管理插件**：静态门 → 契约门 → 评测门 → 红线门，全部自动化；插件间的依赖、seam 使用、数据 schema、迁移全部在清单里显式声明。DeepSeek 的每次交付按门禁证据验收，不靠人肉审代码。
4. **用户侧仪表板必须是客户端原生页面**（关键判断，理由见 §5.1）：插件管理器不能依赖被管理的插件系统，否则插件坏的时候连管理界面都打不开。V1 只做四件事：插件列表、统一更新中心、kill switch、回滚入口。
5. **说明书分层写、随插件包走、客户端内置渲染**：文档版本与代码版本绑定，从根上防止「说明书说的是旧版」。说明书更新纳入发布门——文档不更新，不许发 stable。
6. **顺序建议**：治理基建（本周，纯文档）→ 说明书骨架（随插件栏开发并行）→ 仪表板 V1（随插件栏一起做，正是当前 NEXT.md 排队第 3 的任务）。

## 1. 治理对象：4+1 变更域

这套架构复杂，根源在于它有四个独立演进的主体，加上一条跨主体的暗线：

| 变更域 | 版本载体 | 更新通道 | 变更频率 | 谁在改 |
|---|---|---|---|---|
| ① 客户端 | Electron 包体版本 | 客户端自更新（现有链路） | 低（按需） | DeepSeek 开发，Cyrus 拍板 |
| ② 插件 ×18 | 每插件独立 semver | D1 插件通道（plugins-v*） | 中高（各自独立） | DeepSeek 开发 |
| ③ 模型资产 | models-v* 资产版本 | 独立资产通道（随包/下载） | 低但必然发生（reranker、新嵌入模型） | Cyrus 拍板，manifest 钉哈希 |
| ④ 上游 seam | harness rc 版本（只读） | 不可控，只能观察和适配 | 不可控（rc.8 已证明） | 上游官方 |
| ＋ 数据迁移 | 每插件 schema 版本链 | 随②走，但永久驻留用户机器 | 随插件演进 | DeepSeek 写迁移脚本 |

**治理第一原则：任何变更先归类，再决定流程。** 归类决定：走哪条通道、谁审批、要什么证据、能不能回滚。一次发布里混进两类以上变更（例如「插件更新 + 顺手改 main.js」）是最危险的操作，必须在制度上拆开——D1 已定「客户端版本不为插件动」（D1-07），本文补齐其余边界。

## 2. 未来架构升级会产生什么问题（七类预判与应对）

按发生概率排序。每一条都是「现在不定制度，将来必踩」的坑。

### 2.1 兼容矩阵爆炸（必然发生）

18 个插件 × 若干客户端版本 × 若干模型版本，组合空间是天文数字，全量测试不可能。

**应对**：兼容性不做「全组合验证」，只做「索引钉基线」——每个插件版本在发布索引里钉死它验证过的客户端基线（D1-06），不满足即拒装；CI 只测「当前基线 + 上一基线」两档。用户看到的永远是一个已验证组合，而不是数学上的任意组合。compat.json 升级为机器可读矩阵（见 §3.3），成为唯一事实源。

### 2.2 迁移链断裂（插件独立更新后必然发生）

客户端时代，迁移随客户端版本线性发生；插件独立更新后，用户可能从 memory v0.3 直接跳到 v0.5，跳过 v0.4。迁移脚本如果只考虑「相邻版本」，跳级用户当场坏库。

**应对**：迁移脚本编号化、链式执行、幂等；每个迁移必须支持「从所有仍受支持的旧版本起跳」；发布门的契约测试里固定一条「从最早受支持版本迁移到本版」的用例。这是 V2 通道的硬前提之一（D1 §9.3），此处把它上升为全插件通用纪律。

### 2.3 Seam 漂移（上游不可控，rc.8 已预警）

上游改 seam 语义但版本号小幅变化，插件静默失效——不报错，只是行为错了，最难发现。上游 rc.8（2026-08-19 发布，SQLite 存储不兼容）已经证明这类事件会发生。

**应对**：seam 契约测试（§3.4）双向跑——每次插件发版跑一遍，每次考虑采纳新上游也跑一遍；上游观察例行化（§3.5），每个上游 rc 出「一页影响评估」再决定是否适配，适配决策永远独立于插件发布。

### 2.4 文档腐化（已经在发生）

docs/ 现有 40+ 文件，同一主题多版本并存（记忆系统手册 v1–v4 的演进线、两轮评审稿、Daydream 稿）。人记得哪份是新的，但 AI 开发者（DeepSeek）换 session 后可能读到旧版架构描述，按旧架构写新代码。手册 v4 用「声明唯一权威、吸收评审」的模式解决了记忆系统一个主题，但全库没有制度。

**应对**：权威文档制度（§3.2）——每主题唯一权威文档 + 旧文加 superseded 横幅 + 一份机器可读文档索引。这是本文七件治理基建里成本最低、收益最快的一件。

### 2.5 回滚非对称（V2 插件必然面对）

插件回滚到旧版，但用户数据已被新版迁移——旧插件读新库，轻则报错重则毁数据。V1 通道的零依赖插件无此问题（无状态或状态可重建），memory 这类有库插件是重灾区。

**应对**：迁移感知回滚（D1 §9.3 的 V2 前提）：要么存储前向兼容（新版库旧版可读），要么回滚时明确拒绝并提示「数据已升级，需配套恢复快照」；kill switch 按插件版本粒度生效，出事先止血再谈修复。

### 2.6 用户认知负担（双通道上线即发生）

用户看到「插件更新了」但功能没变（可能只是依赖修复），或者客户端三个月不更新以为产品停更。两条更新节奏必然造成困惑。

**应对**：统一更新中心（§5.2）把客户端/插件/模型三类更新聚合在一个界面，每条更新附一句话人话说明；release notes 按「用户能感知什么」写，不按「开发者改了什么」写。

### 2.7 治理单点（随插件数量增长而恶化）

Cyrus 是唯一审批人。18 个插件各自独立发版后，如果每个版本都要亲自拍板，要么成为瓶颈拖慢发布，要么沦为橡皮图章失去意义。

**应对**：变更分级授权（§3.6）——明确哪些变更类别是「门禁全绿即预授权」的（Class B），只有动架构的（Class A）才需要亲自拍板。管理靠例外，不靠全审。

## 3. 治理基建：提前做的七件事

全是文档/配置制度，不含代码工程。按建议落地顺序排列。

### 3.1 ADR 决策档案

D1 的「核心设计决策」一节（D1-01～D1-10，每条附理由与否决项）已经是 ADR 的雏形，把它制度化为 `docs/adr/`：

- 每条决策一页：编号、日期、状态（生效/被 ADR-xxx 取代）、决策、理由、否决项及否决原因。
- 只追加，不改写；推翻旧决策 = 写新 ADR 标记取代，旧文保留。
- 价值：三个月后问「当初为什么选 GitHub Releases 不选 npm」，不用翻聊天记录；给 DeepSeek 交接时，ADR 是防止它「重新发明已被否决方案」的缰绳。

### 3.2 权威文档制度

- `docs/DOCS_INDEX.md`：全库文档清单，每份标注【权威 / 草稿 / 已被 xxx 取代】+ 适用版本 + 最后核实日期。
- 旧文档顶部加一行横幅：`> ⚠️ 本文已被《xxx》取代（日期），仅留档，勿据此开发。`
- 规则：一个主题永远只有一份权威文档；升级 = 改写权威文档或在原文上出新版并标记旧版，**不新增平行文档**。
- 首批需要加横幅的：记忆系统两轮评审稿、Daydream 稿、检索评测稿（均已被手册 v4 吸收）。

### 3.3 机器可读兼容矩阵

compat.json 已有雏形（harness 版本/commit、运行时版本、插件数、测试状态）。升级为三向矩阵：

- 插件 → 客户端基线（最低/最高验证版本）
- 插件 → 插件依赖（dshComposable 声明，含版本区间）
- 插件 → 模型资产版本（memory 类插件专用）

两个消费方：安装器（不满足拒装）、CI（决定测试范围）。一份文件，人和机器都读它，不允许第二份手写兼容说明存在。

### 3.4 Seam 契约测试

- 静态扫描：插件源码只允许调用 seam 白名单（手册 §9.11.2 那份表），扫描进 CI，私改只读上游 = 直接红灯。
- 运行时烟测：插件加载后对每个声明使用的 seam 做一次探活调用，行为不符即报。
- 双向触发：插件发版时跑，考虑采纳新上游时也跑。后者是 rc.8 类事件的探雷器。

### 3.5 上游观察例行化

- 定期检查上游 release（可用 Automation 定时任务，每周一次足够）。
- 每个新 rc 出一页影响评估：改了哪些 seam、存储是否兼容、我们的插件用到没有、建议「跟进 / 观望 / 冻结在当前基线」。
- 纪律：上游适配永远是独立决策项，绝不与插件发布、客户端发布捆绑（rc.8 已作为待决项挂在 D1 §8）。

### 3.6 变更分级授权

| 级别 | 定义 | 例子 | 授权方式 |
|---|---|---|---|
| Class A | 动架构、动兼容、动数据的变更 | 需要新 seam；新增运行时依赖；不可回滚的迁移；兼容基线上调；新增插件间依赖；模型资产变更 | Cyrus 逐案拍板（附 ADR） |
| Class B | 合同内的增量变更 | 补丁修复；文案调整；评测门内达标的 R 层改进；声明范围内的新工具/新页面 | 四层门禁全绿即预授权，发布总账留痕，Cyrus 事后可查 |

边界写在 ADR 里，DeepSeek 交付时自报级别，报错了也算交付质量问题。这样 Cyrus 的审批只花在真正动架构的地方。

### 3.7 发布总账

`docs/release-notes/` 目录已存在，升级为三线合一的总账：每一次客户端/插件/模型发布，无论走哪条通道，都在总账里登记一行（日期、域、版本、索引哈希、对应 ADR、验收证据链接）。任何时刻都能回答「某个用户机器现在是什么状态、怎么变成这样的」——这是排查「更新后坏了」类问题的唯一可靠入口。

## 4. 开发侧：插件工程管理体系

回答「怎么系统科学地管理插件」。六个字：**声明、门禁、留痕**。

### 4.1 插件模板（脚手架）

所有插件从同一模板生成，模板自带：清单骨架、契约测试骨架、评测脚本桩、迁移目录、README 骨架（= 说明书 L2 页的源文件）。新插件 = 脚手架 + 填业务。D0 的 build-kit / 合同 schema 是现成地基，模板是其自然延伸。价值不在省事，在于**结构一致 → 门禁可以无差别自动化**。

### 4.2 清单即合同（dshComposable 声明全量）

每个插件的清单必须显式声明五件事，缺一项不予发布：

1. **seam 使用**：用了哪些官方 seam（对照白名单）
2. **插件间依赖**：依赖谁、哪个版本区间（memory → project-control / connection-center / skill-library / personal-shell 是现有最大依赖网）
3. **数据 schema**：拥有哪些存储、当前 schema 版本
4. **迁移**：编号迁移脚本清单
5. **模型资产**：依赖哪个 models-v* 资产（仅 memory 类）

声明的意义：安装器据此排序与拒装（D1-09），CI 据此圈测试范围，说明书 L2 页据此半自动生成。

### 4.3 四层门禁（全部自动化，证据可复查）

| 门 | 查什么 | 现状 |
|---|---|---|
| ① 静态门 | typecheck、seam 白名单扫描、清单 lint、许可扫描（记忆插件商用剥离清单已示范） | typecheck 已有；扫描待建 |
| ② 契约门 | 插件对声明 seam 的契约测试；迁移链测试（从最早受支持版起跳） | D0 合同 schema 已有，用例待补 |
| ③ 评测门 | 有质量指标的插件必须带评测脚本，达标才放行；memory 的 R 层 GO/NO-GO 直接映射为发布门 | 记忆评测脚本已有雏形 |
| ④ 红线门 | preflight-publish.js 扩展到插件资产：禁会话记录、禁个人数据、禁密钥、模型哈希比对 | 客户端侧已运行，延伸即可（D1-08） |

### 4.4 双通道发布节奏

- **插件**：独立节奏。开发版验证 → 门禁全绿 → 发 beta（可选）/ stable 索引 → 稳定版更新中心拉取。Cyrus 的两台安装（开发版/稳定版）就是天然的两环灰度：开发版 = ring 0。
- **客户端**：按需，仅在动 Class A 变更时发版。
- **模型资产**：随资产变更独立发 models-v*。
- **铁律**：三类发布互不捆绑；唯一的合法耦合是「插件需要新 seam」→ 触发客户端版本（§2 的边界情形，目前是零）。

### 4.5 交接控制点（对 DeepSeek 的管理界面）

NEXT.md 第 87 行已挂「插件独立更新通道」任务（执行顺序第 3）。每个工作包的交接格式固定四件套：**目标 / 验收标准（可实测项）/ 证据要求（测试输出 + 运行结果 + 文件路径）/ 自报变更级别（Class A/B）**。DeepSeek 不读代码审阅者的角色由门禁替代——门禁证据就是验收证据，这正是「交付必须带可验证证据」规则的制度化。

### 4.6 经验沉淀闭环

WORKING_RULES_AND_PITFALLS.md / 经验.md / NEXT.md「关键坑」段已在做这件事，补一条规则：每次插件发布出事故（含被门禁拦下的），24 小时内沉淀一条进坑清单，格式 = 现象 / 根因 / 检测手段（哪个门该拦它）。坑清单每季度回喂给门禁——能被机器检查的坑，升级成门禁规则，不再依赖记忆。

## 5. 用户侧：仪表板设计

### 5.1 关键判断（2026-08-20 修订）：插件中心做成「内置基线插件」，不做客户端原生页

**Cyrus 反提案**：rc.7 已允许插件接入原生设置面板；插件中心应是一个连通各系统的管理插件，避免用户为管理功能被迫下载新客户端——换端对用户是不可接受的沉没成本。

**实测核实（2026-08-20）：反提案成立，而且它就是现存模式**——

- rc.7 提供 `@deepseek-ai/dsh-client-ui-slots`（命名槽位：sidebar / project.control / conversation / details / workbench.panel / shell.overlay）和 `@deepseek-ai/dsh-client-ui-settings`（设置面板接入），插件可直接贡献管理 UI；
- 插件管理 UI 本来就已经是插件：plugin-organizer（插件清单管理）与 update-center（更新中心）均为插件形态，插件中心 ≈ 合并扩展这两个现存插件；
- personal-shell 的 PanelErrorBoundary 保证单个面板渲染崩溃被隔离、不拖垮整个壳——渲染级自举风险已有工程解法。

**残余风险与两条护栏**：

1. 插件中心必须是**内置基线插件**：随客户端包体分发、不可卸载、永远在场（D1-10）。它自身更新出错时，回滚到的内置基线仍是一个能用的管理器——管理工具不会因自我更新而消失。
2. 插件中心自身更新策略从紧：不自动更新，跟随客户端版本或经 Cyrus 手动确认（它是唯一「半客户端属性」的插件）。

如实说明残余风险：若上游加载器在**加载期**（非渲染期）崩溃，任何插件（含管理器）都起不来，只能靠移除外部插件目录或客户端修复——但客户端原生页面同样依赖客户端运行时桥，这种情况下原生与插件形态差异极小，不构成否决理由。

**结论**：采纳插件形态。本文不再含必须改动客户端代码的决策。

### 5.2 V1 范围（克制，只做四件事）

1. **插件列表**：名称、版本、状态（启用/停用/异常）、所属通道、「可更新」徽标。
2. **统一更新中心**：客户端/插件/模型三类更新聚合一屏，每条附一句话人话说明，一键更新，按 D1-05 提示重启生效。
3. **Kill switch**：每插件一个停用开关，异常插件一键止血（记忆插件的 hybrid 一键关断 `DSH_MEMORY_HYBRID=0` 已示范过这个模式）。
4. **回滚入口**：单插件回滚到内置基线版本（D1-10：内置基线永远在场）。

### 5.3 V2 候选（先登记，不做）

## 6. 用户侧：说明书体系

### 6.1 分层结构

| 层 | 内容 | 篇幅 | 写法 |
|---|---|---|---|
| L0 快速上手 | 装好 → 第一次打开 → 知道什么会自动更新 | 一页，5 分钟读完 | 三个截图 + 五句话 |
| L1 概念页 | 插件是什么、为什么有两种更新、为什么要重启、模型资产是什么 | 一页 | 类比驱动，零术语 |
| L2 每插件一页 | 功能、设置项、数据存在哪、常见问题 | 每插件一页 | 固定五段模板（见 §6.2），由清单半自动生成 |
| L3 故障排查 | 症状 → 检查 → 处置 → 回滚 | 决策树一页起 | 从坑清单反向生成，只写真发生过和可预见的 |
| L4 版本与反馈 | 发布总账的用户可读版、问题反馈通道 | 自动生成 | 从 release-notes 渲染 |

### 6.2 写法原则（五条，全是防腐化机制）

1. **随包绑定**：L2 页放在插件包内（README 源文件），客户端内置帮助中心渲染；L0/L1/L3/L4 随客户端包。说明书版本永远等于代码版本，不存在「网上查到过时说明」。
2. **固定模板**：L2 页五段式——这插件做什么 / 它会动你什么数据 / 设置项 / 常见问题 / 出问题怎么办。模板固定后，AI 可生成、可校对、可批量维护，风格不漂移。
3. **预期管理前置**：记忆系统这类渐进能力，L2 页必须写「当前能做到什么、不能做到什么」（对照 R 层），宁可保守。这类系统最常见的差评来源不是能力差，是用户以为它无所不能。
4. **人话发布说明**：每条更新说明从「用户能感知什么」出发写，开发者视角的变更记录留在总账里，不进说明书。
5. **文档门**：说明书未同步更新的版本，不许发 stable——加进四层门禁的红线门，机器可查（L2 页存在且版本号与插件一致）。

### 6.3 仪表板 vs 说明书的分工

仪表板管「操作」（装/更新/停/回滚），说明书管「理解」（是什么/为什么/怎么办）。两者都要有，但**说明书先行**：它是纯文档工作，现在就可以从模板生成骨架；仪表板随插件栏开发排期（NEXT.md 第 3 顺位任务），V1 克制在四件事。
