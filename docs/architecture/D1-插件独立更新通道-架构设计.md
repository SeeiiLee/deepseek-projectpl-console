## 0. 结论先行

**现状链路（已通）**：开发树（本目录）→ 全量门禁 → 测试版打包 → Cyrus 验收 → 稳定版打包 → preflight → GitHub Releases（`SeeiiLee/deepseek-projectpl-console`，公开仓库）→ 稳定版客户端「更新中心」检查、下载、SHA-256 校验、安装。**客户端通道与 Harness 运行时通道已在跑（v0.1.0 → v0.3.0 已发布）。**

**缺口（要打通的一环）**：插件目前 100% 随客户端包体内置——改一行插件代码也要发整个 ~190 MB 客户端。更新中心对插件只读展示版本号（`bundledPluginVersions`），没有独立的检查/下载/装配能力。

**目标链路（本文设计）**：插件以**预构建 `.tgz` + 机器索引**为单位，经 GitHub Releases 独立标签通道（`plugins-v*`）发布；稳定版更新中心新增「插件」区，完成 **检查 → 下载 → SHA-256 校验 → 装配到外部插件目录 → 重启生效 → 失败回滚到内置版本** 的闭环。简单插件此后不再依赖客户端大更新。

**分期**：

| 期 | 内容 | 对应 NEXT.md 预估 |
|---|---|---|
| V1 最小闭环 | 外部插件目录（优先级高于内置）+ 手动检查 + 下载校验装配 + 重启生效 + 内置回滚 | 2～4 小时 |
| V2 完整版 | 自动检查、更新中心插件 UI、兼容矩阵执行、启动门/doctor 扩展、回滚 UI、beta 通道 | 半天～1 天 |
| V3 标准化 | 激活从私有 overlay 迁到官方 profile bundle（D0.6 遗留项），过 §17.5 全 13 项 | 单独排期 |
| V4 上架/商业化 | npm registry / GitHub topic / 社区市场收录；服务记忆插件剥离 | 时机由 Cyrus 定 |

## 2. 上游官方机制调研（deepseek-ai/deepseek-harness @ GitHub）

来源：上游仓库 `docs/user/develop/basic/publish.zh.md`（rc.7 本地 checkout 与 GitHub 一致）+ Releases 页 + 社区生态实测。

### 2.1 官方分发合同

- **两种 manifest**：组合包（bundle，`dsh.bundle.patch` 指向包内 `cordis.patch.yml`）回答「这个包贡献什么」；profile（`$DSH_HOME/profiles/<name>` 的 `dsh.profile.bundles` 有序列表）回答「这套配置由哪些 bundle 按什么顺序组成」。
- **安装 seam**：`dsh plugin --profile <name> add <pkg|./x.tgz|github:owner/repo>` —— 本质是 pnpm forwarder + bundles reconcile：装完把声明了 `dsh.bundle` 的包追加进 profile 的 bundles 列表，移除则回退。D0 两个 PoC 已实测这条链路（安装 → reconcile → 冷启动 ACTIVE → 移除无残留）。
- **层顺序**：`dsh-base` → 各 bundle patch（按 bundles 列表序）→ profile 自带 patch → home 级 patch → 命令行 `--patch` overlay（**后应用者按 row 胜出**）。当前桌面 overlay 位于最后一层——这既是现状能跑的原因，也是 V1 优先级设计必须处理的点（见 §4 D1-04）。
- **git 安装有坎**：`github:` 安装拉的是源码不是产物，需要作者提供自包含 `prepare` 脚本 + 用户显式授权构建（pnpm ≥10 默认拒绝）。**结论：我们走预构建 tgz，不碰 git 源码安装**（与 D-13 一致）。
- **npm 发布可选**：`pnpm publish` 后 `dsh plugin add <pkg>` 装的就是预构建代码；是否注册 `@cyrus` scope 是 D0.2 遗留决策（当时拍板「先仅 .tgz」，首个公开发布前再定）。
- **rc.7 新 seam**：「各插件可自行注册设置卡片」——V2 插件 UI 可以直接用官方设置卡片，不用自己造入口。

### 2.2 社区生态参照

社区插件市场（dshplugin.app registry、dsh-market、DSH-Plugins-Marketplace 等十余个）**全部围绕同一个官方 seam 构建**：`dsh plugin --profile web add …` + GitHub topic `dsh-plugin` 做发现。没有任何一家绕过 profile/bundle 机制。这印证了 D0/D 系列的方向是对的：V3 迁到官方 profile bundle 后，个人插件即具备被社区市场收录/上架的标准形态。

### 2.3 对我们的三个推论

1. `.tgz + dsh plugin add` 是官方一等公民路径，我们的发布物形态不用再发明轮子。
2. 「发现层」（市场/索引）与「安装层」（profile/pnpm）在社区是分离的——我们的 `plugin-index.json` 就是私有发现层，安装仍走标准机制。
3. 上游破坏性变更（rc.8 存储不兼容）会直接打到插件兼容面——**插件索引必须钉兼容基线**，这是 D1-06 兼容矩阵的现实理由，不是理论洁癖。

## 3. 目标链路总览

```text
开发侧（本目录 = 测试版根）                        发布侧（GitHub 公开仓库）                稳定版客户端
─────────────────────────────   ──────────────────────────────────────   ─────────────────────────────
改插件 → bump 插件版本
→ 单测/结构测试/check:plugins
→ 全量 node --test + smoke
→ pack:dev:portable → packed smoke
→ Cyrus 测试版验收
        │
        ▼（验收通过，仅插件变更时客户端版本不动）
generate-plugin-set --check
→ npm pack（预构建 tgz，files 白名单）
→ 生成 plugin-index.json（版本+SHA-256+兼容基线）
→ preflight-publish 扩展门禁
→ Cyrus 批准
        │                                ┌─ Release: tag = plugins-vYYYY.MM.DD.N
        └──────────────────────────────► │   资产 = *.tgz × N + plugin-index.json + *.sha256
                                         │   （与客户端 vX.Y.Z release 完全分离）
                                         └──────────────┬───────────────────────
                                                        │ HTTPS（更新中心轮询/手动检查）
                                                        ▼
                                         稳定版「更新中心 → 插件」区：
                                         检查索引 → 版本比对（内置 vs 外部 vs 可更新）
                                         → 下载 tgz → SHA-256 对索引
                                         → staging 解压 → 原子换入外部插件目录
                                         → 提示重启 → 启动门校验
                                         → 失败：隔离外部目录，回滚内置基线
```

三条更新通道并存、各自独立节奏：

| 通道 | 发布物 | 触发条件 | 现状 |
|---|---|---|---|
| 客户端 | setup/portable exe + sha256 + blockmap | 壳/Main/打包资产/内置基线变化 | 已通（v0.3.0） |
| Harness 运行时 | git commit → 隔离构建 | 上游 rc 跟进（下次=rc.8 决策） | 已通 |
| **插件** | **.tgz × N + plugin-index.json** | **任一插件版本 bump** | **本文新增** |

## 4. 核心设计决策（D1 系列，每条附理由与否决项）

### D1-01 发布物：预构建 `.tgz` + 机器索引，不碰 git 源码安装

- 每插件 `npm pack` 产出 `cyrus-dsh-<name>-<version>.tgz`（files 白名单、预编译 lib，D-08/D-13）。
- `plugin-index.json` 与 `plugin-set.lock.json` 同源生成（版本、integrity/SHA-256、requires、role、compatibleHarness、minClient、资产文件名），是更新中心唯一信任的插件事实源。
- **否决** `github:` 源码安装：prepare 授权坎 + 供应链面扩大（上游文档自己的警告）。
- **否决** 直接读 GitHub 仓库文件当索引：索引必须与 release 资产同生同灭、不可变。

### D1-02 发布载体：同仓库 GitHub Releases，独立标签命名空间 `plugins-v*`

- 标签形如 `plugins-v2026.08.20.1`（日期 + 当日序号），一次 release 携带当次全部变更插件的 tgz + 一个 `plugin-index.json`。
- **理由**：插件 release 与客户端 release（`vX.Y.Z`）语义解耦——客户端检查器按 semver 过滤标签，`plugins-v*` 天然不会误触发「客户端可更新」；反之插件检查器只认 `plugins-v*` 前缀。
- **否决 A**「插件资产挂在客户端 release 里」：发一次插件就要造一个客户端版本号，用户看到「客户端可更新 v0.3.1」下载 190 MB 发现只改了一个插件——正是要避免的体验。
- **否决 B**「每插件一个 release（`@cyrus/dsh-workbench@0.2.0`）」：18 包 × 多版本的 release 噪音对个人流程是负担；粒度价值留给 V4 单插件商业化（如记忆插件剥离）时再启用，标签规范届时另定。

### D1-03 索引即合同：SHA-256 钉死，不可变 release 兜底

- 更新中心下载 tgz 后必须重算 SHA-256 与索引 `integrity` 逐字比对，不符即拒装（显式失败）。
- GitHub immutable release（上游已启用同款）保证已发布资产不可替换；索引随 release 冻结。
- 现阶段不引入签名：个人单一发布者 + HTTPS + SHA-256 + immutable 已够；**V4 商业化前必须升级签名/校验链**（登记为开放问题 §8）。

### D1-04 装配优先级 V1：外部插件目录 > 内置（junction 重指，不动 overlay）

- 外部目录：稳定版用户数据根下 `plugins-external\<pkg-dir>\<version>\`（稳定版即 `F:\documents\Cyrus Deepseek Harness Data\plugins-external\`），每次装配写入 `.install.json`（版本、tgz SHA-256、来源 release tag、装配时间）。
- 启动时 junction 重指：`ensurePersonalPluginLinks` 逐插件解析——外部目录存在且校验通过（manifest 名/版本/bundle 完整/.install.json 一致）→ junction 指外部；否则指内置。overlay 内容不变，Node 解析到的就是外部新版本。
- **开发版豁免**：开发树启动时 junction 永远指开发 checkout（现状不变），外部目录机制只对打包体生效——否则开发调试会被外部目录截胡。
- **理由**：改动面最小（不动启动链、不动 overlay、不动激活语义），回滚 = 删外部目录，天然满足 NEXT.md「最小版 2～4 小时」量级。
- **明确登记为过渡方案**：overlay 是私有机制，Stock DSH 不认；V3 按 D0.6 迁官方 profile bundle（D-01），届时外部目录退役为普通 profile 依赖，优先级语义由 bundles 顺序接管。V1 选择 junction 方案是因为「先把链路跑通」大于「一步到位」，且 V1→V3 的迁移不破坏已发布插件的索引格式。

### D1-05 安装 = 重启边界，不承诺热重载

- 装配完成后提示「重启生效」（D-10）；Cordis 热重载留给上游成熟后再议。
- 启动门（`verify-launch`）扩展：校验外部插件 bundle 存在/语法/client id 标记，与内置同一标准——坏插件不可能以「看起来正常」的方式进场。

### D1-06 兼容矩阵：索引钉基线，不满足即拒装

- `plugin-index.json` 携带 `compatibleHarness {version, commit}` 与 `minClient`（本次装配所需最低客户端版本）。
- 更新中心检查时发现插件要求高于当前运行时/客户端 → **不显示「更新」按钮**，显示「需先升级客户端/运行时」并指向对应通道。
- 现实案例：rc.8 已发布且存储结构不兼容；本通道先钉 rc.7 基线，rc.8 跟进决策见 §8。

### D1-07 版本纪律：插件独立 semver，客户端版本不为插件动

- 改哪个插件 bump 哪个插件的 `package.json`；lock `--check` 入门禁防漂移。
- 客户端版本只在壳/Main/打包资产/内置基线变化时 bump——这就是本通道存在的意义。
- 例外：插件依赖新的桌面桥能力（如新的 preload API）时，`minClient` 抬升，客户端必须先发版——由索引显式表达，不靠默契。

### D1-08 发布纪律：红线门禁延伸到插件资产，发布仍需 Cyrus 批准

- `preflight-publish` 扩展到插件发布物：逐 tgz 核对 `npm pack` 清单（files 白名单）、扫描包内个人路径/密钥模式（D-11）。
- GitHub token 只从 keyring 读取；release notes 人工脱敏复核（现有规则不变）。
- dev 打包产物永不当发布资产（既有纪律）。

### D1-09 依赖闭包与顺序

- 单插件更新：要求该插件的 `requires` 在当前安装集合中已满足，否则拒装并列出缺失项（复用 D0 installer 的 add-check 语义）。
- 一次 release 多插件更新：按索引 `installOrder` 顺序装配，任一失败则本次全部回滚，不留半集合状态。
- 新增必需依赖（如 workbench 新增 requires）视为破坏性变更：必须在 release notes 明示，且检查期校验闭包。
- **V1 边界**：junction 装配不运行依赖安装，因此 V1 只放行**零运行时依赖**插件（当前 18 占 16）；含 `dependencies` 的插件（memory、project-control）在 V2「依赖供给」落地前不进入外部更新通道，仍随客户端基线更新（见 §9）。

### D1-10 回滚：内置基线永远在场

- 内置插件随客户端包体永远存在，是天然回滚位；回滚 = 隔离外部目录（quarantine，保留 `.install.json` 证据）→ junction 落回内置 → 重启。
- 另保留上一外部版本一个档位（`plugins-external\_backup\`），支持「回滚到上一外部版」而不必一路退回内置。
-  doctor 校验失败（fiber 非 ACTIVE、bundle 缺失）→ 自动隔离 + 提示，绝不带伤运行（显式失败优于静默降级）。

## 5. 全流程跑道（逐步）

### 5.1 开发（开发树，现状不变）

1. 改 `plugins/<name>/`，bump 其 `package.json` 版本。
2. 插件单测/结构测试 → `pnpm run check:plugins`（含 bundle-identity）→ 全量 `node --test` → `pnpm run smoke`。
3. 涉及分发的插件按 §17.5 子集补证：pack 清单、干净 profile 安装、冷启动 ACTIVE。

### 5.2 测试版验收（现状不变）

`pack:dev:portable` → `smoke:packed:dir:dev` → Cyrus 双击测试版验收。

### 5.3 插件发布（新增跑道，暂名 `release:plugins`）

1. `generate-plugin-set.mjs --check` 与 manifest 一致。
2. `npm pack` 当次变更插件（V1 从简：全量 18 包重打也可以，资产 KB~百 KB 级）。
3. 生成 `plugin-index.json`（含 SHA-256、兼容基线、minClient）。
4. preflight 扩展门禁通过；release notes 脱敏。
5. **Cyrus 批准** → 建 GitHub Release `plugins-v*` → 上传 tgz + 索引 + .sha256。
6. 稳定版客户端无需重新打包（除非 minClient 抬升）。

### 5.4 稳定版更新（客户端侧）

1. 更新中心「插件」区：手动「检查插件更新」（V1）/ 随客户端检查自动触发（V2）。
2. 拉最新 `plugins-v*` release → 下载索引 → 三态比对（内置版本 / 外部版本 / 可更新版本）。
3. 用户点「更新」→ 逐插件下载 → SHA-256 对索引 → staging 解压 → 原子换入外部目录 → 写 `.install.json`。
4. 提示重启 → 启动门 + junction 重指 → fiber ACTIVE 校验。

### 5.5 回滚

一键「回滚到内置」/「回滚到上一版」→ 隔离外部目录 → 重启 → doctor 复核。

### 5.6 首次引导（bootstrap）

本通道能力本身（更新中心插件区 + 外部目录装配 + 启动门扩展）**随一次普通客户端更新（建议 v0.4.0）落地**。这是唯一一次「插件功能要靠客户端更新」——之后插件独立飞。

## 6. UI 方向（只定形态，不写代码）

- **更新中心**：三通道并列卡——客户端 / Harness 运行时 / 插件。插件卡内逐行：名称、当前版本（徽标：内置/外部）、可更新版本、兼容状态、「更新」「回滚」按钮、重启提示条。
- **插件整理（plugin-organizer）**：显示每个插件的来源（内置/外部-版本号）与安装时间，与更新中心联动跳转。
- **入口**：优先复用 rc.7「插件自行注册设置卡片」官方 seam，不造第二套设置入口（架构红线 8）。

## 9. 复杂插件专题：记忆系统的发布路径（2026-08-20 Cyrus 询问，实测结论）

### 9.1 实测事实基线

| 关切点 | 实测结果 | 证据 |
|---|---|---|
| 代码形态 | 记忆系统**已经是一个插件**：Host 逻辑全在 `plugins/memory`（打包 lib ≈ 202K），Client 为设置卡片；Electron main 内**没有**记忆业务代码 | `plugins/memory/` |
| main 进程耦合 | `src/main.js` 仅有 6 个 `DSH_MEMORY_*` 环境变量注入（数据根、模型目录解析、提取/自测开关）——是配置接线，不是功能 | `src/main.js:165-188` |
| 加密链路 | SQLCipher 在插件 Host 进程内；DPAPI 由插件侧调 PowerShell `ProtectedData` 完成，**不经 Electron safeStorage**，无客户端耦合 | `plugins/memory/lib/index.js`（dpapiInvoke） |
| 运行时依赖 | `dependencies` = better-sqlite3-multiple-ciphers / @huggingface/transformers / onnxruntime-node；插件自带 node_modules（开发树 36M）；tgz 的 files 白名单**不含** node_modules → 依赖必须在安装期解析 | `plugins/memory/package.json` |
| 模型资产 | bge-m3-onnx 560M 数据目录，env 解析（显式覆盖 > flavor 默认）；当前随客户端包体分发（v0.3.0 包体 +83MB 的主因），发布红线要求干净副本 + manifest SHA-256 比对 | `docs/PUBLISHING_RULES.md`、`F:\…\models\bge-m3-onnx` |
| 全局依赖盘点 | 18 插件中仅 memory（重原生）与 project-control（ajv/ajv-formats，纯 JS 小件）有运行时 dependencies，其余 16 个为零依赖 | 逐包 package.json 扫描 |

### 9.2 判断：记忆系统可以纯插件化——它距离「纯插件」只差资产拆分，不差架构改造

把「记忆系统」拆成三条道，每条道各有归属，不存在「没办法」的部分：

1. **代码道** = 插件 tgz（KB 级）→ 走 `plugins-v*` 通道。P5 记忆智能层（Context Compiler / Recall Orchestrator 等）全部是 Host 侧插件代码，天然在这条道。
2. **模型/数据道** = 版本化模型资产包：发 `models-v*` 标签 release（或挂插件 release 附件），SHA-256 对 `docs/p4-model-manifests/` manifest，下载一次落入数据根 `models\` 目录。模型更替是稀有事件，不配跟代码同节奏。此后客户端包体可以卸下模型（回到 ~108MB 量级），首次安装由更新中心/记忆设置卡引导下载模型包；保守路线是客户端继续内置基线模型、模型包通道只服务换模型/升级——二选一，建议前者。
3. **运行接线道** = main.js 的 env 注入：保持稳定、通用、少动。记忆系统未来若需要新的桌面能力（新 env、新桥接 API），攒批进偶发客户端版本，索引用 `minClient` 显式抬升——这正是 D1-07 的例外条款，不是漏洞。

### 9.3 复杂插件进通道的两个前提（属 V2，V1 不含）

1. **依赖供给**：含运行时 dependencies 的插件，外部装配必须补依赖解析——安装期在外部目录执行受限 `pnpm install --prod`（与官方 profile 安装同语义），或发布时用 bundleDependencies 打自包含 tgz；失败显式报错并回退内置基线。落地前 memory 不走外部通道。
2. **数据迁移感知回滚**：记忆插件带 SQLite migrations，回滚不能只看代码——被新版本迁移过的库，旧版本未必能读。规则：迁移前自动做加密快照（复用现有快照机制）；回滚检测到库版本高于插件可读版本时，提示「回滚需同时恢复快照」并给一键组合回滚；迁移只进不退、fail closed。

### 9.5 P4/P5/P6 全部工作项的插件化映射（2026-08-20 复核记忆全组文档后登记）

依据文档：记忆系统手册 v4（唯一权威，已吸收两轮评审）、P5 统一架构、P4 方案与路线图。结论：**P4/P5/P6 的设计全部落在已验证的插件 seam 内，可以纯插件模式实现**；v0.3.0 的 P0–P4 + P6-1 已经以纯插件形态上线，就是活证据。

| 工作项 | 性质 | 通道 |
|---|---|---|
| P0–P3 可信基座（分片/FTS/显式工具/候选提取） | 已上线，纯插件 | 插件通道 |
| P4 Hybrid（bge-m3 向量/RRF/降级） | 已上线；代码纯插件，模型为数据资产 | 代码=插件；模型=`models-v*` |
| P6-1 稳定化（恢复/shadow import/reset/迁移演练） | 已上线，纯插件 | 插件通道 |
| P6-0C/2 Codex 导入（盘点/解析/提取/全量批处理） | Host 批处理 + 迁移 | 插件通道 |
| S0（factual_at v5/backfill、治理 UI、512 修复） | schema 迁移 + Host + viewer | 插件通道 |
| P5-R1 Context Compiler / 多路召回 / rerank | Host 服务；Kernel/Catalog 走 `systemPrompt.section` 小契约，Task Pack 走任务级注入 | 插件通道 |
| P5-R2 Curator / Admission / Doctor | Host 后台任务（effect 定时器）+ 迁移 | 插件通道 |
| P5-R3 Procedure / Outcome | Host；提升 Skill 走 skill-library 插件 bridge | 插件通道 |
| P5-R4 Latent Cue / Reflection / 可选 graph | Host；vendor graph/ANN 若引入 = npm 依赖声明（D-09），非客户端改动 | 插件通道 |
| Reranker/新模型资产（如本地 cross-encoder） | 数据资产 | `models-v*` 模型包通道 |
| main.js 的 `DSH_MEMORY_*` env 接线扩展 | Electron 壳 | 客户端通道（稀有，攒批） |

五个必须守住的插件化重点：

1. **seam 白名单纪律**：只用已验证 seam（`systemPrompt.section` / `tools` / `webServer` / `credentials` / session 事件 / quick-pass 注入 / effect+disposer / viewer 注册）；`systemPrompt.context` 明令禁止承载召回；想要的 seam 上游没有 → 停下仲裁，不改只读上游。
2. **插件间依赖显式化**：memory 依赖 project-control（身份 Host API）、connection-center（提取连接）、skill-library（M2 提升）、personal-shell（UI slot）——requires/bridges 必须进 dshComposable 与索引，D1-09 依赖闭包门禁强制执行。
3. **V2 两前提先落地**：依赖供给（onnxruntime/SQLCipher 安装期解析）+ 迁移感知回滚（P5 每层 R 都有 schema 演进，快照先行、组合回滚）。
4. **模型资产独立通道**：bge-m3 及未来 reranker 模型走 `models-v*`，SHA-256 对 manifest；插件 tgz 永不背模型权重。
5. **评测门 = 发布门**：P5 各 R 层的 GO/NO-GO 直接映射为插件版本 + config kill switch；评测不过就不发该层插件版本——插件通道让「哪层过门发哪层」的纪律变便宜，不再攒大版本。

### 9.4 记忆系统发布节奏结论

| 变更类型 | 通道 | 频率 |
|---|---|---|
| 日常记忆开发（P5 智能层、召回、提取等） | 插件通道 `plugins-v*`（V2 起） | 高频 |
| 换模型 / 模型升级 | 模型资产包 `models-v*` | 稀有 |
| 新桌面能力（env/桥接） | 客户端版本 + `minClient` 抬升 | 稀有 |
| 商业化剥离 | D1-02 例外：单插件独立 release 轨道 / npm scope 决策（§8 开放问题 5）；模型按 PUBLISHING_RULES「用户自备模型」模式绕开权重分发 | 时机 Cyrus 定 |
