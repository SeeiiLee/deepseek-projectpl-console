# D3 全局项目文档与文件治理体系（跨项目复用）

> 状态：架构设计稿，待 Cyrus 拍板。不写代码。
> 定位：D2 管「DSH 插件体系」的治理；本文把治理推广到**所有项目**（DSH、食溯、未来更大型项目）的文档与文件结构。日期：2026-08-20

---

## 0. 结论先行

1. **docs 不平铺，立分支目录**。两个项目的现状（DSH docs 40+ 平铺、食溯 docs 30+ 平铺）已经证明平铺必然失控；按「文档类型」建 12 个标准子目录，类型由目录承载，文件名回归简洁。
2. **十类文档全覆盖清单**：日志、PRD、架构、设计、评审、交接、验收/评测、发布、规则、决策（ADR），外加附件与归档两个特殊区。Cyrus 提到的七类全部在内，补的三类（评审/验收/决策）正是 AI 协作开发最缺的。
3. **每主题一份权威文档**的制度从 DSH 推广到所有项目；旧文档不删，加横幅或进 archive。
4. **骨架进项目模板**：标准 docs 结构纳入项目模板（PROJECT_TEMPLATE_SPEC 的模板注册表），新建项目自动落骨架——食溯、未来项目开局即合规，不靠事后整理。
5. **不搞大搬家**：存量两个项目三步迁移（先索引、新文档按新结构、旧文档按需归档），避免一次性重命名断掉所有交叉引用。
6. **文件树/文件类型的「产品级」结构化管理**属于工作台功能需求（非本文档目录约定），单独登记进 NEXT.md 交给 DeepSeek（见 §7）。

## 1. 问题实证（两个项目现状对照）

| | DSH Personal docs/ | 食溯 meal_tracker docs/ |
|---|---|---|
| 规模 | 40+ 文件平铺 + 4 个临时子目录 | 30+ 文件平铺 |
| 命名习惯 | D0/D1 编号、P4/P5 阶段号、全大写主题、中文主题混用 | 里程碑号（M6_/M7_DESIGN）、HANDOVER_*、AUDIT-日期、DEPRECATED_ 前缀 |
| 多版本并存 | 记忆手册 v1–v4 + 两轮评审稿 | DEPRECATED_ 前缀处理废止（好惯例，值得推广为制度） |
| 交叉引用 | 文档间互相引用文件名，重命名即断链 | 同左 |
| 子目录 | agent-instructions/、memory/、p4-model-manifests/、release-notes/（无统一规则，临时生长） | 无 |

结论：问题不是「懒」，是**没有分类学和放置规则**。AI 协作者（DeepSeek/Codex/Kimi）每次写文档都按当下直觉命名放置，熵只增不减。

## 2. 文档分类学（十类 + 两个特殊区）

| 类 | 目录 | 现存例子 | 权威规则 |
|---|---|---|---|
| ① 决策 | `adr/` | D1 的 D1-01～10 决策节（应拆出） | 只追加不改写，推翻 = 新 ADR 取代 |
| ② 规则/治理 | `governance/` | PUBLISHING_RULES、PROMPT_AND_AGENTS_GOVERNANCE、AGENTS 引用规则 | 变更需 Cyrus 拍板 |
| ③ PRD/需求 | `prd/` | FEATURE_IMAGE_VISION、食溯 requirements | 一需求一文档，状态字段必备 |
| ④ 架构 | `architecture/` | 架构设计、D1、D2、工作台-项目控制台联动架构设计书 | 每主题唯一权威 |
| ⑤ 设计（模块/阶段） | `design/` | M6_*/M7_*/M9_DESIGN、P4/P5 方案稿 | 按里程碑/阶段组织，收尾后可归档 |
| ⑥ 评审 | `reviews/` | 记忆系统两轮评审、Codex试点盲评、RICH_TEXT_EDITOR_PHASE1_REVIEW | 评审稿永不改写，结论被权威文档吸收后归档 |
| ⑦ 交接 | `handoff/` | NEXT、HANDOVER_*、HANDOFF_*、PROGRESS | 活跃交接一份（NEXT），历史交接归档 |
| ⑧ 验收/评测 | `verification/` | P4-2-验收方案、Markdown走查测试、检索评测 | 带日期与结论，与发布总账互链 |
| ⑨ 发布 | `release/` | release-notes/（迁入）、compat.json | 即 D2 §3.7 发布总账载体 |
| ⑩ 日志 | `logs/` | DEVLOG、PROGRESS、经验 | 追加式，永不改写历史 |
| 特殊区 附件 | `attachments/` | p4-model-manifests/、FEATURE 图片、合同 JSON | 按主题再建一层子目录 |
| 特殊区 归档 | `archive/` | 被取代的旧文档 | 只进不出，文件名保持原样 |

每个目录里允许按主题再建一层子目录（如 `design/m6/`、`attachments/models/`），**不允许第三层**——层级超过三，查找成本重新失控。

## 3. 命名规范（三条）

1. **类型前缀废止**：类型由目录表达，文件名不再带 HANDOVER_/DEPRECATED_/AUDIT- 等前缀（食溯的 DEPRECATED_ 惯例升级为「进 archive + 顶部横幅」）。
2. **文件名 = 主题[-限定].md**：中文或英文均可（与现况一致），限定词按需用日期（`-2026-08-20`）或版本（`-v4`）；架构级保留 D 编号传统（`architecture/D1-...`）。
3. **永远不改名**：文件一旦被其他文档引用，改名 = 断链；要废就归档，不改名。

## 4. 生命周期（与 D2 §3.2 同源，推广到全项目）

```
草稿（任意目录，标「状态：草稿」）→ 权威（标「状态：权威」+ 进 INDEX）
→ 被取代（顶部横幅「已被 xxx 取代」+ 移入 archive/）→ 永不删除
```

- 一个主题同一时刻只有一份权威文档；升级 = 在原文档出新版并归档旧版，**不新增平行文档**。
- 评审稿、评测稿是例外：它们天生是快照，写完即冻结，不需要「权威化」。

## 5. 索引：`docs/INDEX.md` 唯一入口

- 人机双读：每份文档一行——路径、类型、状态（权威/草稿/已取代）、适用版本、最后核实日期、一句话内容。
- 新增/归档文档必须同步改 INDEX，否则文档门（D2 §6.2）拦截。
- 机器可读性预留：INDEX 的表格结构固定，未来 project-control 可直接解析进项目数据库，工作台文件树按类型着色/分组的数据源就是它。

## 6. 多项目复用：骨架进项目模板

- 把 §2 的标准骨架（12 个空目录 + INDEX.md 模板 + governance/README 一份治理规则）注册进**项目模板**（PROJECT_TEMPLATE_SPEC §1 模板注册表），新建项目时由 project-control 的 Write Plan 自动落盘。
- 各项目可在骨架上加自己的子目录（如食溯的 `design/m6/`），不允许删骨架目录——保证 AI 协作者跨项目切换时结构直觉成立。
- 项目级 AGENTS.md 只需引用一句：「文档治理见 docs/INDEX.md 与 governance/」。

## 7. 与工作台/项目控制台的联动（区分两个层面）

Cyrus 提到「文件树、文件类型的管理必须结构化、多项目复用」——这包含两个不同层面，分开管：

| 层面 | 谁管 | 本文的角色 |
|---|---|---|
| ① 仓库目录约定（docs 怎么放、怎么命名） | 本文 + 项目模板 | 直接规定 |
| ② 工作台内的文件树渲染、文件类型注册、文档管理 UI（如按类型分组、按状态着色、INDEX 可视化） | 产品功能，交 DeepSeek | 本文的目录约定与 INDEX 是②的数据基础 |

②的需求登记进 NEXT.md：「工作台文件树支持按 docs 治理分类学分组显示；文档状态（草稿/权威/已归档）从 INDEX.md 解析」。不在这轮开发范围内，排队。

## 8. 存量迁移策略（不搞大搬家）

一次性重命名/移动 40+ 文件会断掉全部交叉引用，风险远大于收益。三步走：

1. **第一步（本周，纯文档）**：建 INDEX.md，把现有文件逐条登记进分类学（文件不动，索引先行）；给已被取代的旧文档加横幅（D2 §3.2 首批：记忆系统四份旧稿）。
2. **第二步（即刻起，零成本）**：新文档一律按新结构放置；D1/D2/D3/D4 直接落 `architecture/`。
3. **第三步（惰性归档）**：旧文档只有在「被引用修改」或「被取代」时才顺手移入对应目录/archive，并同步修引用。预计 2～3 个月自然收敛，不追求一次到位。

食溯项目同理，由 OpenClaw 或下一次食溯 session 按同一规则执行。
