## 0. 一句话定位

说明书是写给 LLM 的操作规程；**Project Console 是它的机器执行面**。
说明书 §10 的五个不变量（INDEX 双向一致 / 位置正确 / 状态头 / 取代必有横幅 / ADR 只追加），本质上是五个可计算函数——这正是控制台该做的事。

**第一原则（继承 P5 红线，不可协商）**：文件是唯一事实源。Console 只读、诊断、提议、复验，**永不代写 docs 内容，永不把正文入 DB，永不因文本语气推进任何状态**。

## 1. 底座盘点：控制台已有什么（不要重建）

| 已有能力 | 来源 | 治理视图怎么用 |
|---|---|---|
| 有界文档读取（单文件 8 MiB / 总量 64 MiB / 5000 项）、逐绑定 hash、解析诊断 | P5 document-index | R1/R2 层直接复用 |
| 重绑提案 → 人工确认（Proposal 交互范式） | P5 | 治理诊断的修复提案复用同一交互 |
| 单项目页签：Overview / Checklist / Reviews / Agent Runs / Activity / Documents / Sessions | P7 | 新增 Governance 页签，不动现有页 |
| Session 指令路由、capability 握手 | P6 Gate 2E | 治理上下文注入 agent session 的通路 |
| 模板 Write Plan 三模板（minimal/software/research） | P1/P3 | 说明书 §8 第 5 条已要求模板自动完成治理初始化——这是"出生即合规"通路 |

注意：扩展 document-index = 新 migration + 新 capability，而 project-control 合同族是冻结的——**本次扩展本身必须走 ADR（Class A）**，治理系统治理它自己。

## 2. 读取：三层模型

- **R0 结构层**：十二目录骨架在位情况（核心目录 adr/governance/architecture/design/handoff/release/logs/archive 必须存在）；根 AGENTS.md 是否含 §0 速查卡；INDEX.md 是否存在。产出：骨架报告。
- **R1 元数据层**：逐文档解析状态头（首 5 行：权威/草案/活跃/留档）；解析 INDEX 表格（路径→状态→说明）；解析 adr/ 目录（编号/标题/状态：生效/预登记/被取代）。容错解析，失败只记 parse issue（P5 已有机制），不硬报错。
- **R2 不变量层**（说明书 §10 L1 的机器形态）：
  1. **INDEX 双向一致**：docs 下每个 .md 都有 INDEX 条目；每个条目都指向存在的文件（两个方向，豁免集合需定义：attachments/ 与 archive/ 是否全量登记）；
  2. **位置正确**：INDEX 每行目标目录 vs 实际路径，惰性留根名单以 INDEX 标注为准；
  3. **状态头存在且合法**：首 5 行有合法状态词；
  4. **取代必有横幅**：留档文档含「本文已被」横幅且指向存在的继任者；
  5. **ADR 只追加**：adr/ 文件与上次快照 hash 比对，内容被改写即报警（合法变迁白名单：仅状态字段 生效→被 ADR-xxx 取代）。
  6. **（跨项目追加，来自 §12）说明书副本版本漂移**：各项目治理说明书副本的版本号 vs 主副本 v1.0——这是唯一一条项目级而非文档级的不变量。

## 3. 呈现：两个界面 + 一个升级

- **项目级 Governance 页签**（与 Overview/Documents 并列）：
  - 健康卡：六条不变量红绿灯 + 骨架完整度 + AGENTS 速查卡在位状态；
  - **权威清单**：当前生效的权威文档 + 生效 ADR 列表 = agent 开工前的最小阅读集（这是给 LLM 看的，也是给人看的）；
  - 诊断列表：每条违规 → 可生成 Proposal（应用/忽略，复用 P5 重绑提案交互）；
  - 交接新鲜度：活跃交接文档（NEXT.md）最后更新距今、四件套齐缺（目标/验收标准/证据要求/自报级别）。
- **跨项目治理总览**（所有项目总览页加治理摘要列）：每个项目一行健康摘要；缺 AGENTS、INDEX 过期、未接管（§9 流程未跑）的项目一眼可见。
- **Documents 面板升级**：从平铺列表到按治理目录分组 + 状态徽章 + 横幅标记——倾向并入 Governance 页签，避免两个文档视图（待参考工作台定夺）。

## 4. 起效：五条通路（按杠杆排序）

1. **E0 模板通路（杠杆最高，说明书 §8-5 已授权）**：升级三个内置模板，新项目 Write Plan 直接产出骨架目录 + INDEX 模板 + AGENTS 速查卡 + 首份 ADR——**出生即合规，预防优于检测**。
2. **E1 门禁通路**：五不变量做成一条 CLI 进 preflight 族（已登记 NEXT.md「治理门禁脚本任务」）；CLI 与 Console 面板共享同一计算核心，一处实现两处呈现。
3. **E2 会话通路**：经 P6 session 路由，agent 打开项目时收到治理上下文卡（权威清单 + 失败不变量 + 交接文档指针）——L0 强制曝光除 AGENTS.md 外多一条机器推送通道。
4. **E3 提案通路**：诊断 → Proposal → 人/agent 确认 → 执行方改文件 → Console 复验（hash 变化后诊断自动消除）。修复动作永远在 Console 之外发生。
5. **E4 审计通路**：周期全量扫描（发布前/每周），健康度趋势入审计报告；失效模式按说明书 §10 L2 沉淀进坑清单，能机器化的升级为新的不变量（系统自我硬化）。

## 5. 分期

| 期 | 内容 | 风险 |
|---|---|---|
| 一期：只读诊断 | R0–R2 + Governance 页签 + 诊断列表 | 零写入，最低 |
| 二期：提案闭环 + 模板升级 | E3 + E0 | 模板 Write Plan 属冻结合同扩展，先 ADR |
| 三期：门禁 + 会话注入 | E1 CLI + E2 上下文卡 | 门禁接入 preflight 族需全量回归 |

每期独立交付价值；一期先跑起来，哪怕只实现六条不变量里的前三条。

## 6. 开放问题（等 Cyrus 的参考工作台到位后对齐）

1. **健康度形态**：离散六灯 + 逐项钻取，还是聚合成单一健康分？（倾向离散灯——分数会掩盖具体哪条挂了；但跨项目总览可能需要一个可排序的聚合值）
2. **诊断→修复的交互形态**：沿用提案列表（P5 范式）？任务化 checklist？还是联动聊天让 agent 直接领修？——这是最该参考成熟工作台的一点（GitHub code scanning / JetBrains inspections / Linear 的 triage 各有范式）。
3. **未治理项目的呈现**：「未接管」作为显式状态 + §9 接管向导入口，还是只显示骨架缺失？（倾向前者：未治理不是错误，是一个待办状态）
4. **ADR 只追加的验证基线**：hash 快照存 project_document_states 还是独立治理快照表？合法状态变迁白名单的精确语法。
5. **会话上下文卡的格式归属**：归 project-control 契约族扩展（走 Class A ADR），还是归 P6 外部输入适配器？
