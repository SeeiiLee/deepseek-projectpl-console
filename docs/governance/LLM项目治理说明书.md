# LLM 项目治理说明书（通用版）

> 版本：v1.1 ｜ 状态：权威 ｜ 主副本：Deepseek Harness Personal `docs/governance/`（2026-08-20 建立，2026-08-25 按 ADR-009 增补 Project Home 三分区）
> 读者：任何 LLM 协作者（DeepSeek / Codex / Kimi / GPT / OpenClaw 等）。
> 用途：新项目按 §8 初始化；存量项目按 §9 接管；日常开发按 §0–§7 执行。
> 本说明书自身的修订走 ADR（§5），各项目副本须带版本号并定期与主副本同步（§12）。

## 0. 速查卡（直接复制进项目 AGENTS.md，这是强制执行点）

```
## 文档治理（创建/修改 docs 下任何文件前必读）
1. 完整规则见 docs/governance/LLM项目治理说明书.md；本卡是摘要，冲突以说明书为准。
2. 一个主题只有一份权威文档；新增平行文档 = 违规。
3. 类型由目录承载：adr/ governance/ prd/ architecture/ design/ reviews/
   handoff/ verification/ release/ logs/ attachments/ archive/。
4. 每份文档首 5 行内必须有状态声明：权威 / 草案 / 活跃 / 留档。
5. 新建/修改/归档任何 docs 文件，必须同步更新 docs/INDEX.md（双向一致）。
6. 永不改名、永不删除；被取代 = 加横幅（模板见说明书 §3）。
7. 架构级决策写 ADR（docs/adr/，只追加不改写）；交付自报变更级别
   （Class A = 动架构/兼容/数据，需所有者拍板；Class B = 其余）。
8. 交付必须带可验证证据：测试输出 / 运行结果 / 文件路径。
```

## 1. 五条核心原则（每条附一句"为什么"）

1. **唯一权威**：一个主题同一时刻只有一份权威文档——否则换 session 的 LLM 会读到旧版，按旧架构写新代码。
2. **类型由目录承载**：类型进目录，文件名只写主题——命名前缀（HANDOVER_/DEPRECATED_ 等）会腐烂，目录不会。
3. **永不改名、永不删除**：改名断掉所有交叉引用；被取代的文档加横幅或进 archive/，历史永远可追溯。
4. **写入即登记**：任何 docs 文件的增改必须同步 INDEX.md——索引与文件不一致 = 索引失去意义。
5. **交付带证据**：LLM 的每次交付附测试输出/运行结果/文件路径——验收看证据，不看叙述。

## 2. 目录骨架与文档分类

### 2.0 外层 Project Home（三分区）

本节表格描述 `workspace/docs` 内部结构；项目在机器上的外层结构统一由 [`统一项目目录与三分区治理合同.md`](统一项目目录与三分区治理合同.md) 管理：

```text
F:\Projects\<project-slug>\
├─ workspace\   canonical 项目根（本说明书和下表在这里生效）
├─ worktrees\   开发 checkout，不放进 workspace
└─ local\       运行时/构建/E2E/cache/receipt，不进 Git/发布/默认记忆扫描
```

项目性质、生命周期和归档状态进 Project Control 元数据，不通过搬动 Project Home 表达。路径不是身份；三个分区必须绑定同一 `project_id`。

| 目录 | 放什么 | 核心目录? |
|---|---|---|
| adr/ | 架构决策记录（只追加） | 是 |
| governance/ | 规则、红线、本说明书 | 是 |
| prd/ | 产品需求 | 可裁 |
| architecture/ | 架构设计（D 级） | 是 |
| design/ | 模块/阶段设计（里程碑级） | 是 |
| reviews/ | 评审稿（写完即冻结） | 可裁 |
| handoff/ | 交接文档（活跃交接只留一份） | 是 |
| verification/ | 验收、评测、走查 | 可裁 |
| release/ | 发布总账、release notes、兼容矩阵 | 是 |
| logs/ | DEVLOG、经验、坑清单 | 是 |
| attachments/ | 图片、manifest、合同 JSON（可按主题再分一层） | 可裁 |
| archive/ | 被取代的文档（只进不出） | 是 |

规则：允许按主题再建一层子目录（如 `design/m6/`）；**不允许第三层**；核心目录不可删；项目可在骨架上加自己的目录，加目录 = 更新 INDEX 并在本说明书的项目副本里登记。

## 3. 文档生命周期与操作清单

状态机：`草案 → 权威/活跃 → 留档（横幅）→ archive/`。评审稿、评测稿写完即冻结（直接留档）。

**新建文档**：定类型 → 选目录 → 命名（`主题[-YYYY-MM-DD 或 -vN].md`，禁类型前缀）→ 首 5 行写状态声明 → 登记 INDEX。

**升级权威文档**：在原文档上出新版（状态头更新日期/版本），旧版加横幅后移 archive/（或被多处引用时原位加横幅、惰性迁移）。

**取代横幅模板**（加在被取代文档首行标题之后）：

```
> ⚠️ 本文已被《xxx》（路径）取代（日期，拍板人）。仅留档，勿据此开发。索引见 docs/INDEX.md。
```

## 4. INDEX.md 维护规程

- 格式：每份文档一行——路径、状态、一句话说明（可按目录分节，参考主副本的 INDEX.md）。
- 更新时机：新建、归档、状态变更、目录调整——**与文件操作同一次提交/交付内完成**，不后补。
- 双向一致的定义：docs 下每个 .md 都在 INDEX 有条目；INDEX 每个条目都指向存在的文件。

## 5. ADR 规程

- 何时写：Class A 变更（动架构/兼容基线/数据 schema/新增依赖）**必须**先有 ADR；有值得记录的否决方案时**应该**写。
- 格式：状态（生效/预登记/被 ADR-xxx 取代）、背景、决策（编号）、否决项及原因、影响。一页以内。
- 铁律：只追加不改写；推翻旧决策 = 新 ADR 标记取代，旧文保留。

## 6. 交接规程

- 活跃交接文档只有一份（如 NEXT.md）；历史交接加横幅或移 archive/。
- 每个工作包四件套：**目标 / 验收标准（可实测）/ 证据要求 / 自报变更级别**。
- 「关键坑」清单持续追加：现象 / 根因 / 检测手段；能被机器检查的坑应升级为门禁规则。

## 7. 红线（违反 = 交付打回）

1. 不改名、不删除任何 docs 文件。
2. 不开平行文档（同主题第二份"权威"文档）。
3. docs 内不放密钥、个人数据、会话记录正文（随包发布物另受项目发布红线约束）。
4. 不伪造状态头与 INDEX 条目（写了「权威」就必须是权威）。
5. 不把「待核实」内容当事实引用——标注不清的按待核实处理。

## 8. 新项目初始化流程（LLM 按序执行）

1. 由受控 Host 在 `F:\Projects\<project-slug>` 建立 Project Home；目标必须 absent/空，并创建 `workspace/worktrees/local` 三分区与 project-home marker。
2. 只在 `workspace` 创建 §2 骨架目录（含核心目录）；`worktrees/local` 不得嵌入 canonical Git 工作区。
3. 落 INDEX.md 模板（空表 + 状态图例）。
4. 把 §0 速查卡写入 `workspace/AGENTS.md`（**强制曝光点，不可省略**）。
5. 落第一份 ADR：项目初始化决策（目标、范围、不做清单）。
6. 生成 `.dsh-project/project.yaml`，确保 Project Home marker、workspace manifest 和 Project Control binding 使用同一 `project_id`。
7. 为 local 写入 retention policy/ledger 初始状态，为 worktrees 写入空 registry；二者默认排除于 Git、发布与记忆正文扫描。
8. DSH 体系项目：以上步骤必须由新版本 Project Home + Template Write Plan 原子完成；现有已发布模板 1.0.0 不得原地扩展。手工初始化只能用于隔离 fixture，不得冒充 Console 已支持。

## 9. 存量项目接管流程（LLM 按序执行）

1. **盘点**：列出 docs/（或等价目录）全部文件，不做任何移动。
2. **建 INDEX**：每文件一行；没读过的状态一律标「待核实」，禁止凭文件名猜「权威」。
3. **识别权威与废弃**：与所有者确认各主题的权威文档；被取代的加 §3 横幅。
4. **即日起新文档按本说明书执行**；旧文件惰性迁移（被修改/被取代时才移位）。
5. **不搞大搬家**：不批量移动、不批量改名（断链风险大于整洁收益）。
6. 向所有者输出盘点报告：文件总数、权威清单、待核实清单、建议动作。

## 10. 执行保障：三层独立机制（单层必失效，三层才可靠）

**L0 入口层——强制曝光**：速查卡（§0）写进 AGENTS.md，每个 harness 每次 session 启动自动读到；LLM 不点开说明书也会看到八条铁律。新项目由模板注入，存量项目由所有者/LLM 按 §9 写入。

**L1 过程层——机器可查的五个不变量**（每条规则配检查，无检查的规则等于没有规则）：

| # | 不变量 | 手动验证（LLM 可直接执行） |
|---|---|---|
| 1 | INDEX 双向一致 | 列 docs 全部 .md，逐一比对 INDEX 条目（两个方向） |
| 2 | 位置正确 | 文件位于其类型目录，或在 INDEX 标注的惰性留根名单内 |
| 3 | 状态头存在 | 抽查首 5 行有 权威/草案/活跃/留档 字样 |
| 4 | 取代必有横幅 + INDEX 状态更新 | grep「本文已被」与 INDEX 留档条目交叉核对 |
| 5 | ADR 只追加 | adr/ 内文件无内容改写痕迹（版本控制或修改记录可查） |

脚本化门禁（把五项检查做成一条命令、进 preflight 族）是该机制的硬化形态，实现为工程任务排队（见各项目 NEXT/交接文档）；脚本缺失时，手动验证是底线。

**L2 验收层——人与审计兜底**：交付验收单固定含「治理合规」一项（INDEX 同步？位置正确？自报级别合理？）；每次发布前或每周跑一次 L1 全量检查；发现违规**修复不追责**——但失效模式必须沉淀进坑清单，能机器化的升级为 L1 新不变量。

**为什么是三层**：LLM 可能不读说明书（L0 挡）、读了可能不执行（L1 挡）、检查可能没跑（L2 挡）；三层失效相互独立，同时失效的概率才可接受。

## 11. Session 结束自检清单（LLM 在被要求时输出）

- 本轮新建/修改/归档的 docs 文件清单
- INDEX.md 是否同步（双向）
- 新文档状态头、目录位置
- 是否有文档被取代 → 横幅与 INDEX 状态
- 是否触发 Class A → ADR 编号
- 自报变更级别复核

## 12. 本说明书自身的治理

- 版本号语义化（v1.0 起）；修订走 ADR，重大修订需所有者拍板。
- 主副本：Deepseek Harness Personal `docs/governance/LLM项目治理说明书.md`。
- 各项目副本在首部标注版本与同步日期；与主副本冲突时以主副本最新版为准，并回填项目差异为项目附录（不改主规则）。
