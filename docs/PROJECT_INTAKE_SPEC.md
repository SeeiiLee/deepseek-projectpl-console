## 1. 目标

项目控制台必须同时服务两类真实使用场景：

1. 用户已经拥有大量项目，只需定位项目目录和文档目录，就能批量发现、导入并生成项目概览。
2. 用户需要快速建立新项目，通过版本化模板直接进入标准管线。

这两个入口最终必须汇入同一套项目身份、文档映射和 Project Protocol。导入旧项目不要求立即改造目录；新项目从创建开始遵守标准。本文件冻结接入行为；配套的数据结构与机器 Schema 分别由 `PROJECT_CONTROL_DATA_MODEL.md`、`PROJECT_PROTOCOL.md` 和 `protocol/project-control/v1alpha1/lifecycle/` 定义。Gate 2C 已实现扫描、候选审阅、授权引用、只读关联与安全重绑；这不代表 Gate 2D 的模板写盘、文件同步或标准新建已经实现。

## 2. 核心原则

- **先发现，再确认**：扫描结果只是候选项目，不能自动注册成正式项目。
- **默认只读**：扫描、识别、预览和导入为 `linked_legacy` 都不修改项目目录。
- **证据可追溯**：自动提取的名称、目标和文档角色必须显示来源文件；无法确认时显示“未识别”，不能猜测。
- **一个事实一个来源**：文档内容以项目文件为事实源；项目路径、登记状态和用户选择保存在全局控制面；协议语义由版本化 Project Protocol 定义。
- **身份与路径分离**：项目移动不等于新项目，路径也不能充当项目 ID。
- **显式标准化**：只有新建项目或用户确认“升级为受管理项目”时，系统才可以写入标准目录。
- **不阻断会话**：项目接入发生在 Project Console 与 Workbench，完整 Conversation 始终保留并继续可用。
- **先兼容旧项目，再推动新标准**：旧项目可长期保持 `linked_legacy`；标准日志流水线只对 `managed` 项目强制执行。

## 3. 术语与身份

| 术语 | 定义 |
| --- | --- |
| 项目来源目录（Source Root） | 用户授权扫描的父目录，例如 `D:\Projects`。它属于全局设置，本身不一定是项目。 |
| 项目根目录（Project Root） | 一个项目的工作目录，代码、资料或其他项目内容位于其中。 |
| 文档目录（Docs Root） | 项目内承载 PRD、日志、架构等资料的目录；可以是项目根目录，也可以有一个主文档目录和多个附加文档目录。 |
| 项目候选（Candidate） | 扫描发现但尚未登记的目录，只能用于预览和确认。 |
| 文档映射（Document Map） | 将实际文件或目录映射到 PRD、进展、下一步、架构、ADR 等标准角色的选择结果。 |
| 受管理目录 | 项目内的 `.dsh-project/`，用于放置 Project Protocol 所需的可移植元数据和标准文档入口。 |
| 路径绑定（Location Binding） | 全局控制面保存的项目身份与当前机器绝对路径之间的关系。 |

项目名称不承担身份作用。重名项目允许存在，必须由稳定项目身份和路径绑定区分。

## 4. 三种项目状态

### 4.1 `discovered`

- 来源目录扫描到的候选，还没有加入项目总览。
- 可以查看识别结果、冲突和文档预览。
- 重新扫描后可以更新或消失；它不拥有 WorkItem、Run 或审核状态。
- 对项目目录零写入。

### 4.2 `linked_legacy`

- 用户已确认加入控制台，但项目没有有效的标准 manifest。
- 项目名称、显示目标和文档映射可以来自自动识别或用户确认。
- 控制台只索引已有资料；不会移动、重命名、重排或格式化文件。
- 可以使用项目概览和文档刷新，但标准事件、受控日志写入、Run 审核管线等能力必须明确标为“升级后可用”。
- 用户可以长期停留在该状态。

### 4.3 `managed`

- 项目具有有效且受支持的 Project Protocol manifest 和稳定项目身份。
- 新建标准项目直接进入此状态；旧项目经明确确认后可以升级到此状态。
- 文档可以继续保留在原位置，由 manifest 记录角色映射；升级不要求搬迁现有资料。
- 后续 Agent 日志、事件、Artifact 和审核进入版本化标准管线。

允许的主要转换：

```text
discovered ──确认导入──> linked_legacy ──确认升级──> managed
     └────────按标准接管───────────────> managed
快速新建标准项目──────────────────────> managed
```

`managed` 项目的 manifest 缺失或损坏时，状态变为“需要处理”，不能静默降级成 `linked_legacy`。从控制台移除项目只移除全局登记和路径绑定，不删除项目文件，也不删除 manifest。

## 5. 统一接入入口

Project Console 的项目总览提供一个“添加项目”入口，展开三个动作：

1. **扫描项目来源目录**：适合一次发现多个已有项目。
2. **导入单个已有项目**：适合直接选择确定的项目根目录。
3. **快速新建标准项目**：适合从模板创建新目录并立即进入 `managed`。

当前 Gate 2C 已开放前两个动作；第三个动作及所有需要创建项目文件的路径留在 Gate 2D，界面和 Host 都不得伪造创建成功。

无论从哪个入口开始，确认页都必须呈现相同的核心信息：

- 项目根目录；
- 识别或填写的项目名称；
- 一句话目标及其来源；
- 主文档目录和附加文档目录；
- PRD、进展日志、下一步、当前架构和 ADR 的映射；
- 目标状态：`linked_legacy` 或 `managed`；
- 将写入项目目录的文件清单；默认应为“无”。

## 6. 批量扫描项目来源目录

### 6.1 配置来源目录

- 用户可以登记多个来源目录，并为每个来源目录设置显示名称和是否自动刷新。
- 默认只检查来源目录的直接子目录；用户可以将扫描深度提高到有限层级，但界面必须显示预计范围。
- 扫描不得越过用户选择的来源目录边界，不跟随会逃逸到边界外的符号链接、junction 或其他重解析点。
- 固定跳过 `.git`、`node_modules`、构建产物、依赖缓存、回收站和受管理目录内部等明显非项目目录。
- 权限不足、路径不可访问、文件过大或编码无法安全读取时记录问题，不能让整个批次失败。

### 6.2 候选识别

目录满足以下任一条件时可以成为候选：

- 存在受支持的 `.dsh-project` manifest；
- 存在版本库标记或常见项目清单，并且目录不是已知依赖/构建目录；
- 存在可识别的 README、PRD、DEVLOG、架构或同类核心文档组合；
- 用户在结果页手动把一个未自动识别的目录标记为项目。

识别强度只决定排序和提示，不决定自动导入。候选显示“高/中/低证据”，并列出命中的标记。

### 6.3 扫描结果

批量结果按以下状态分组：

- 新发现；
- 已登记且正常；
- 路径已移动或不可访问；
- 身份/路径冲突；
- 已忽略。

用户可以多选无冲突候选并批量加入为 `linked_legacy`；任何需要写项目目录、存在多重文档映射或身份冲突的候选必须逐项确认，不能混在“一键全部导入”中。

“忽略”只在全局控制面记录，不在项目目录创建隐藏文件。用户随时可以取消忽略。

Gate 2C 实现说明：目录必须经系统选择器授权；授权为单次、短期并绑定“来源目录”用途。Host 默认只扫描直接子目录，按规范化路径展示每个项目的最新候选，同时保留历史 scan job 供审计；重复扫描会继承同一路径的忽略状态。当前确认动作按候选逐项进行，批量多选执行仍可在不改变本节语义的前提下后续补充。

## 7. 单个已有项目导入

单项目导入流程固定为：

1. 选择项目根目录。
2. 自动寻找文档目录和文档角色。
3. 展示项目名称、目标、文档映射、冲突和证据来源。
4. 用户修正文档目录或映射。
5. 选择“只关联现有项目”或“按标准接管”。
6. 显示最终影响预览并确认。
7. 加入项目总览；失败时保持项目目录原状并给出可恢复说明。

默认主按钮是“只关联现有项目”，结果为 `linked_legacy`。只有用户主动选择“按标准接管”并通过写入预览后，才创建受管理元数据并进入 `managed`。

Gate 2C 实现说明：单项目目录同样必须经系统选择器签名授权。`linked_legacy` 确认已经可用；“按标准接管”只在目录原本已有有效、受支持 manifest 时可以无写入地登记为 `managed`。把没有 manifest 的 legacy 项目升级为 `managed` 仍属于 Gate 2D，当前不会创建 manifest。

## 8. 文档目录与角色识别

### 8.1 文档目录候选

系统在有界范围内依次检查：

1. 有效 manifest 已声明的文档位置；
2. 项目根目录；
3. 根目录下名为 `docs`、`doc`、`documentation`、`documents` 或大小写等价的目录；
4. 用户手动添加的项目内目录。

自动检测不能无界递归整个仓库。主文档目录用于默认展示，附加文档目录用于补充映射；同一个项目允许 README 在根目录、PRD 在 `docs/`、ADR 在另一个子目录。

### 8.2 标准文档角色

| 角色 | 常见候选 | 识别结果 |
| --- | --- | --- |
| 项目说明 | `README.md`、Overview/Home 文档 | 0 或 1 个主文件，可保留附加说明 |
| 产品需求 | `PRD.md`、`PRD_*.md`、Requirements/Product Spec | 0 或 1 个当前主文件，历史版本作为附加资料 |
| 进展日志 | `DEVLOG.md`、`PROGRESS.md`、Changelog/Updates | 可以映射一个主日志或一个更新目录 |
| 下一步 | `NEXT.md`、Roadmap/Plan | 0 或 1 个主文件 |
| 当前架构 | `ARCHITECTURE.md`、Architecture/Design 文档 | 0 或 1 个当前主文件，可保留附加设计资料 |
| 架构决策 | `decisions/`、`adr/`、ADR 文件集合 | 0 或 1 个主目录 |

文件名只提供候选证据。选择“当前 PRD”或“当前架构”时，应同时展示标题、相对路径、修改时间和短预览，不能只凭最近修改时间静默决定。

### 8.3 项目名称与一句话目标

项目名称的默认优先级：

1. 有效 manifest 中的明确名称；
2. 用户指定的主 PRD 一级标题；
3. 主 README 一级标题；
4. 项目文件夹名。

一句话目标只从明确的结构化摘要、`目标/Goal/Objective` 段落或用户输入中产生。找不到清晰句子时显示“未识别”，不把随意的 README 首段或模型推测当作项目目标。

每个自动值必须附带来源路径；用户可以设置仅用于控制台显示的覆盖值。对 `linked_legacy` 项目，这类覆盖值保存在全局控制面，不反写文档。项目生命周期、健康度和“是否完成”不得从日志语气自动推断。

### 8.4 映射预览

预览必须让用户直观看到：

- 哪些文件已匹配到标准角色；
- 哪些角色缺失；
- 哪些角色有多个候选等待选择；
- 哪些内容互相矛盾；
- 系统会读取什么、会写入什么；
- 每个自动提取字段的来源。

用户可以将文件设为“附加资料”或“不参与索引”。“不参与索引”只影响 Project Control，不删除或修改原文件。

Gate 2C 的候选详情已经在 Workbench `Details` 中展示名称/摘要来源、证据、问题、相对路径、标题、短预览和内容哈希，并允许修正文档角色或排除索引。候选预览不会把整份文件复制进数据库或开发日志；确认前会重新读取所选文件并核对 SHA-256。

## 9. 冲突处理

以下情况一律停止自动确认并进入逐项处理：

| 冲突 | 必须提供的处理 |
| --- | --- |
| 多个 PRD/架构文件都像当前版本 | 预览差异，由用户指定主文件，其余保留为附加或历史资料 |
| README、PRD、文件夹给出不同项目名 | 展示所有来源，由用户选择显示名称；不改源文件 |
| 文档目标互相矛盾 | 标记“资料不一致”，保留来源，不生成综合结论 |
| 已存在但无效/不受支持的 manifest | 只读展示错误；用户修复或走明确迁移，不能覆盖 |
| 同一路径已绑定其他项目身份 | 阻止重复登记，进入身份处理 |
| 同一项目身份同时出现在两个可访问位置 | 要求选择移动重绑、只读镜像或另存为分支项目 |
| 新建目标目录非空 | 停止创建；改为导入，或选择新的空目录 |
| 文档位于项目根目录之外 | 默认拒绝映射；只有未来明确的外部资料引用能力可支持 |
| 文件读取失败或疑似二进制 | 记录问题并跳过，不以空内容覆盖已有索引 |

冲突页必须把“系统建议”与“已确认事实”分开。没有用户决定时，候选保持原状态。

## 10. 旧项目升级为受管理项目

升级是可选动作，不是导入的隐含步骤。升级前必须完成：

1. 验证项目目录可写且没有路径逃逸。
2. 验证没有现存的未知或无效 `.dsh-project` 内容。
3. 固定当前文档映射，保留现有文件位置。
4. 展示将创建的目录和文件，以及不会被修改的现有文件。
5. 由用户明确确认。

升级只创建最小的受管理元数据和必要目录，不自动重写 PRD、README、DEVLOG，不把 `NEXT.md` 条目自动转成 WorkItem，也不把历史日志自动转换成正式 Event。

升级写入必须是可恢复的原子操作：任一步失败就撤销本次新建内容，项目继续保持 `linked_legacy`。升级完成后，后续管线根据 manifest 声明的 Project Protocol 版本工作。

Gate 2B 的 `project.upgradeManaged` payload 只提交 Host 签发的 `locationRef`、当前 location revision、legacy fingerprint hash 和精确 write plan，不携带绝对路径。write plan 只允许新增不存在的目录/文件。没有 Gate 2D 文件同步 capability 时，Host 必须返回 `CAPABILITY_NOT_NEGOTIATED`；只有同步状态为 `committed` 且 manifest 字节 hash 复验一致后，命令才可 accepted、把 mode 改成 `managed` 并产生 lifecycle Event。

## 11. 快速新建标准项目

新建流程固定为：

1. 选择一个已登记来源目录或其他父目录。
2. 填写文件夹名、项目名称和一句话目标。
3. 选择模板及模板版本。
4. 预览将创建的完整目录和文件。
5. 确认目标目录不存在或为空。
6. 原子创建项目并登记为 `managed`。
7. 在 Project Console 打开项目概览；Conversation 不自动切换或新建 Session。

Gate 2B 的 `project.createFromTemplate` payload 使用 Host 签发的 `sourceRootRef` 与预检 `targetLocationRef`，同时冻结模板 hash、manifest hash 和逐项 write plan，不接受调用方传入任意绝对路径。Gate 2B 未启用 Gate 2D 原子模板同步时只能返回 rejected；未来只有文件同步 `committed` 后才可登记 managed Project 并产生 `project.managed.created`。

第一批内置模板只包含：

- **最小标准项目**：项目说明、PRD、进展入口、下一步和受管理元数据。
- **软件项目**：在最小模板上增加当前架构、ADR 目录和测试/验收说明。
- **研究项目**：在最小模板上增加研究计划、证据记录和决策目录。

模板只负责起始文件布局，不定义不同的核心状态机。模板文件必须包含清晰的待填写提示，不能生成看似已经确认的目标、成功标准或进展事实。

## 12. 模板与协议版本

Project Protocol 版本和模板版本是两个独立概念：

- **Project Protocol 版本**定义项目身份、文档角色、标准输入输出和事件语义。
- **模板版本**定义新项目最初获得哪些目录和样板文件。

每个新建项目记录创建时使用的模板身份与版本。模板发布后不可原地改写；修订必须产生新版本。已有项目不会因为客户端更新而自动套用新模板。

“升级模板”必须是显式操作，先显示逐文件新增/修改预览，再由用户确认；默认只补充缺失文件，不覆盖已有内容。协议迁移由独立迁移流程负责，不能伪装成模板升级。

## 13. 项目移动、重新绑定与分支副本

### 13.1 移动或改名

- `managed` 项目移动后，系统通过稳定项目身份识别原项目，并提示把路径绑定更新到新位置。
- 只有旧位置不可访问且新位置身份一致时，才可以建议“一键重新绑定”；执行前仍需确认。
- `linked_legacy` 没有项目内稳定身份时，只能依据只读指纹提供候选匹配，不能因名称相同自动重绑。
- Windows 路径大小写、盘符和重解析点必须规范化后比较，避免同一路径重复登记。

Gate 2C 已实现 `managed` 的安全重新绑定：新位置 manifest 身份必须与已登记项目一致，并且旧 active 位置确实不可访问；否则候选保持冲突。确认命令使用 Host 签发的候选引用并在事务中同时更新 location 和候选状态。`linked_legacy` 的启发式移动匹配仍不自动执行。

### 13.2 复制、克隆或分支

当两个可访问目录含有同一项目身份时，系统不得把它们同时当作两个可写主项目。用户必须选择：

- **移动后的新位置**：更新原项目路径，旧位置解除绑定；
- **只读镜像/备用位置**：保留一个主位置，另一个不参与写入管线；
- **注册为分支项目**：为副本生成新的项目身份，并记录来源关系。

生成新身份会修改副本的受管理元数据，必须先展示写入预览并确认；原项目身份和历史不被改写。Git worktree、仓库 clone 与项目身份不是同一概念，不能仅凭 Git remote 自动合并项目。

## 14. 全局与项目内事实归属

| 信息 | 归属 | 说明 |
| --- | --- | --- |
| Project Protocol 语义和支持版本 | 应用随附的全局不变契约 | 由版本化实现发布，不由单个项目自定义 |
| 模板目录和不可变模板版本 | 全局模板目录 | 新建时读取；不会后台改写已有项目 |
| 来源目录、忽略项和扫描偏好 | 全局控制面 | 与当前机器有关，不写入项目 |
| 项目绝对路径、路径历史、主/镜像位置 | 全局控制面 | 机器本地事实，不进入可移植 manifest |
| 自动识别结果、导入问题和用户显示覆盖 | 全局控制面 | 可重新扫描；不得覆盖项目文档事实 |
| 稳定项目身份、协议版本和相对文档映射 | 项目内受管理元数据 | `managed` 项目可随目录移动 |
| PRD、日志、架构和 ADR 正文 | 项目文件 | 文件是内容事实源，控制台只索引和呈现 |
| WorkItem、Run、Review、Event、Outbox | 后续全局项目数据库 | 属于事务控制事实；结构边界见数据模型，运行时从 Gate 2B 实现 |
| Session 全文和工具调用 | Harness 原生存储 | Project Control 只保存后续关联，不复制全文 |

同一字段不得在全局数据库、manifest 和文档中各自维护一份可独立编辑的值。全局“显示覆盖”必须明确标注为界面偏好，不能冒充对 PRD 的修改。

## 15. Project Protocol 输入与输出边界

本接入规格冻结接入语义。Gate 2A 由 `PROJECT_PROTOCOL.md` 冻结 manifest、External Runtime Update Command、Normalized Event 与 progress frontmatter；Gate 2B 由 `protocol/project-control/v1alpha1/lifecycle/` 冻结 `registerLegacy`、`registerManaged`、`createFromTemplate`、`rebindLocation`、`upgradeManaged` 的 Envelope/payload、Result 与 normalized lifecycle Event；Gate 2C 为 register/rebind 补齐了与候选绑定的 Host-issued 路径引用与 resolver。两组命令 kind 和 capability 互不重叠。

接入管线的输入包括：

- 用户授权的来源目录或项目根目录；
- 有界扫描选项；
- 自动发现的文档候选及读取问题；
- 用户确认的项目名称、目标、文档映射、状态选择和写入许可；
- 新建项目的模板选择与版本。

接入管线的输出包括：

- 可丢弃的项目候选和证据；
- 已确认的项目登记与路径绑定；
- 角色明确的文档映射；
- `linked_legacy` 或 `managed` 状态；
- 可审计的导入、重绑、升级或创建结果；
- 需要人工处理的问题，不产生伪造的领域状态。

未来其他 Harness 应用必须调用同一接入服务或 Project Protocol 接口，不能直接编辑全局数据库，也不能自行发明第二种 manifest、日志状态或项目 ID。

## 16. 四栏界面呈现

Gate 2A 延续 Gate 1 的固定布局：

```text
Harness 原生侧栏 | Project Console | 完整 Conversation | Workbench
```

- Project Console 已承载“来源目录/单项目选择、候选列表、导入状态和确认动作”。
- Workbench 的 `Details` 已通过 `project-control.candidate-details` viewer 承载所选候选的文档预览、证据来源、映射和影响预览。
- Conversation 始终保持完整挂载、可阅读和可输入；打开批量扫描或接入流程不得把它替换成全屏向导。
- 宽屏下可以同时显示候选列表、Conversation 和 Workbench 预览。
- 中窄屏下，候选详情可以在 Project Console 内切换为二级页面；只有用户主动查看文件时才展开 Workbench。返回动作必须回到原候选和滚动位置。
- 不创建覆盖 Conversation 的大型模态框。系统文件夹选择器可以短暂出现，但完成选择后立即回到四栏界面。
- 批量操作显示已选择数量、可直接导入数量、待逐项处理数量和执行进度；失败项可以单独重试，不阻塞已成功项。

## 17. 默认无写入合同

以下动作对项目目录必须为零写入：

- 登记或刷新来源目录；
- 批量扫描；
- 打开候选预览；
- 自动识别名称、目标和文档角色；
- 导入为 `linked_legacy`；
- 修改全局显示名称、忽略项或路径绑定；
- 检查升级影响。

Gate 2C 已对上述扫描、候选审阅、忽略/恢复、文档映射、`linked_legacy` 登记和 managed 重新绑定落实零写入路径；目录选择授权、扫描结果和忽略项只进入全局控制面。

只有以下动作允许写项目目录，并且必须先显示精确影响预览：

- 快速新建标准项目；
- 将旧项目升级为 `managed`；
- 把复制目录注册成具有新身份的分支项目；
- 用户以后通过受控 Project Protocol 管线明确发起的文档写入。

任何接入动作都不得自动执行 Git commit、安装依赖、启动 Agent、创建 Session、删除文件、移动文件或发送外部请求。

## 18. 第一个可用闭环

完整接入闭环固定为：

1. 用户添加一个包含多个现有项目的来源目录。
2. 系统完成有界扫描并展示候选、证据和问题。
3. 用户选择一个项目，确认主文档目录及 PRD/DEVLOG/架构映射。
4. 项目以 `linked_legacy` 加入总览，项目目录没有任何变化。
5. 用户在外部编辑 DEVLOG 后刷新，控制台显示新的文件版本和来源。
6. 用户把该项目升级为 `managed`，确认页只创建受管理元数据，不重写旧文档。
7. 用户从版本化模板快速新建另一个标准项目，新项目直接出现在总览。
8. 客户端重启后，来源目录、项目身份、路径绑定和文档映射保持一致；Conversation 的原生状态不受影响。

这个闭环不包含 WorkItem 创建、Agent 调度、日志事件入库、审核或 Workbench 文件编辑；这些能力由后续 Gate 建立在本契约之上。

Gate 2C 已完成步骤 1–4 的只读发现与确认关联基础，以及来源/候选/忽略状态的持久化和候选详情 viewer。步骤 5 的项目文件刷新/索引同步、步骤 6 的 legacy 升级和步骤 7 的模板新建仍属 Gate 2D；不得因为 Gate 2C 能识别文档就宣称这些步骤已完成。

## 19. Gate 2A 验收矩阵

本 Gate 以规格冻结为交付物；后续实现必须把下列场景转成自动或人工验收。任何一项违反“默认只读、身份稳定、来源可追溯、Conversation 不被替换”都视为阻断。

| ID | 场景 | 期望结果 |
| --- | --- | --- |
| IN-01 | 添加含多个仓库的来源目录 | 有界扫描得到候选；依赖/构建目录被跳过；项目目录零写入 |
| IN-02 | 候选只有 README 和 PRD | 显示识别证据，可导入为 `linked_legacy`，缺失角色明确标记 |
| IN-03 | 同时存在多个 PRD | 不自动选择当前版本；用户逐项确认后才可完成映射 |
| IN-04 | README、PRD 与目录名冲突 | 展示全部来源；用户选择显示名称；源文件不被改写 |
| IN-05 | 无法提取一句话目标 | 显示“未识别”，不生成模型推测 |
| IN-06 | 批量选择十个无冲突候选 | 可一次登记为 `linked_legacy`；每项结果独立，失败不回滚其他成功项 |
| IN-07 | 候选含身份或 manifest 冲突 | 从批量确认中剔除并进入逐项处理，不覆盖现有内容 |
| IN-08 | 单项目只关联 | 全局登记成功，项目目录的文件清单和哈希均不改变 |
| IN-09 | 旧项目升级为 `managed` | 先显示写入清单；只创建最小受管理内容；旧 PRD/日志保持原位和原文 |
| IN-10 | 升级中途失败 | 撤销本次新建内容，项目仍为 `linked_legacy`，显示可恢复错误 |
| IN-11 | 在非空目录快速新建 | 阻止覆盖，建议改为导入或选择空目录 |
| IN-12 | 从三类内置模板新建 | 记录模板及版本，创建内容与预览一致，项目直接为 `managed` |
| IN-13 | 客户端升级后模板出现新版本 | 旧项目不自动变化；显式升级前提供逐文件预览 |
| IN-14 | `managed` 项目移动到新路径 | 通过稳定身份识别并经确认重绑，项目历史不分裂 |
| IN-15 | `linked_legacy` 同名目录出现在另一位置 | 只给候选匹配，不自动重绑或合并 |
| IN-16 | 复制 `managed` 项目造成重复身份 | 阻止双主写入；可选择重绑、只读镜像或生成新身份的分支项目 |
| IN-17 | 映射文件位于来源边界外或经链接逃逸 | 拒绝读取/映射并给出明确路径安全问题 |
| IN-18 | 修改外部 DEVLOG 后刷新 | 索引显示新版本和原始来源，不把文本自动转换为已批准状态 |
| IN-19 | 打开批量接入和文档预览 | Project Console/Workbench 承载流程；完整 Conversation 始终存在且可继续输入 |
| IN-20 | 从控制台移除项目 | 只删除全局登记；项目目录、manifest 和文档均保留 |
| IN-21 | 重启客户端 | 来源目录、忽略项、路径绑定、状态和文档映射恢复一致 |
| IN-22 | 其他 Harness 应用接入同一项目 | 通过同一 Project Protocol/服务识别身份，不直接写数据库或创建第二套格式 |

## 20. 明确后置

- 数据库、迁移运行时、Host API 与 lifecycle dispatch 基础已由 Gate 2B 实现；Gate 2C 已实现项目来源/单项目扫描、候选审阅、授权引用签发、register/rebind resolver 和只读文档映射。
- 项目文件持续刷新/索引同步、模板/升级的原子文件同步与标准新建仍在 Gate 2D；在 Gate 2D 之前 create/upgrade 不得伪造成功。
- 标准日志 Renderer、ADR 与 Artifact 输出适配器的运行时实现；固定 frontmatter 和最小正文合同已由 Project Protocol 定义。
- WorkItem、Run、Session/Agent 绑定和调度的运行时实现。
- 把历史日志自动转换为领域 Event。
- Workbench 文件编辑、Diff、Browser 和终端实现。
- Git commit、远程仓库同步和多设备自动合并。
- AI 自动修复文档冲突、自动判断项目完成或自动批准导入。

后续 Gate 必须在不改变本文件核心语义的前提下实现存储和接口；如果实现发现需要改变项目状态、无写入边界、身份规则或输入输出归属，应先回到产品决策，而不是在数据库或 UI 中隐式改变契约。
